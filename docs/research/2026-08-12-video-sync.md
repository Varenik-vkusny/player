# Синхронизация видео со звуком проекта — спайк S13

Дата проверки: **2026-08-12**
Машина: Windows 11, Chromium из Playwright, окно настоящее (не headless),
звуковое устройство настоящее. Ничего параллельно не выполнялось.

Оснастка: `spikes/s13-video/`, скрипты замеров — см. §6.
Материал сгенерирован ffmpeg 8.1.1: в файле **вспышка кадра и щелчок в звуке
поставлены на одну метку времени**, поэтому картинку и звук можно сверять
между собой, а не только каждое с часами.

---

## §1. Главное

**Видео может играть синхронно со звуком, НЕ становясь источником времени.**
Инвариант №1 нарушать не требуется: видео ведомое в том же смысле, в каком
ведомым является таймлайн по инварианту №2, — с той разницей, что сверять
его нужно редко, потому что собственный ход у него ровный.

**Способ «выставлять `currentTime` каждый кадр» негоден** — не по цене,
а по картинке: она идёт втрое реже с провалами почти в секунду.

## §3. Что из этого следует для устройства

**Видео пускается по расписанию, а не «когда дойдёт очередь».** Вся точность
синхронизации сводится к моменту вызова `play()`: измерено, что задержка старта
на 60 мс даёт постоянный сдвиг −40…−47 мс, который потом никуда не уходит.
Это тот же приём, которым в S9 закрыт стык сегментов: стык **планируется,
а не обнаруживается**.

**Сверка нужна как страховка, а не как рабочий режим.** За минуту порог 250 мс
не был превышен ни разу. Механизм обязан существовать (декодер может залипнуть
на слабой машине или при смене вкладки), но в норме он молчит.

**Доводка через `playbackRate` отвергнута замером,** а не по вкусу: ±3 % дали
121 кадр назад за минуту. Кадр назад — это видимый рывок, а у говорящей головы
рывок заметнее, чем сдвиг на полкадра.

## §4. Ловушка, которая стоила прогона

**Без `Accept-Ranges: bytes` перемотка не выполняется, и молча.**
Записали `video.currentTime = 5` — чтение возвращает 0. Через 300 мс тоже 0.
Ни ошибки, ни предупреждения; событие `seeked` не приходит вовсе.

Первый прогон дал из-за этого «браузер показывает 1 кадр за 60 секунд» —
вывод правдоподобный, архитектурный и целиком порождённый моим сорокастрочным
тестовым сервером. Второй прогон дал «расхождение растёт до 10.8 с» — тоже
оснастка: проверка перемотки оставляла видео на 12-й секунде, и прогон
начинался не с нуля.

Отсюда в оснастке появились две проверки, которые падают громко:
`serve-range.mjs` умеет диапазоны, а прогон бросает, если перед стартом
видео не на нуле (`spike-video-sync.mjs`).

**Это тот же класс, что «своим парсером свой формат не проверяется».**
Мерил браузер, а измерял свою оснастку — дважды, и оба раза результат
выглядел как содержательный вывод об устройстве браузера.

## §5. Оговорки, без которых числа врут

- **Вспышки измерены с шагом кадра (33.3 мс), звук — с точностью 2 мс.**
  Поэтому «сдвиг 0 мс» доказано строго только для звука относительно
  медиавремени файла. Этого достаточно: губы привязаны к `mediaTime`.
- **Материал — сгенерированный, а не съёмка человека.** Щелчок против вспышки
  строже губ (те заметны от ~80 мс), но настоящее лицо в живом редакторе
  на приёмку глазами всё равно нужно.
- **Одна машина, один браузер, Windows.** Ни Android, ни iOS не проверены —
  это тот же незакрытый долг, что у ADR-002.
- **Файл 60 с, 1280×720, 611 кбит/с.** Более тяжёлое видео может залипать
  чаще; порог сверки взят с запасом именно поэтому.
- **`playbackRate`-доводка отвергнута на коэффициентах ±3 %.** Мягкие
  (±0.5 %) не пробовались: они не понадобились, раз дрейфа нет.

## §6. Чем прогонять

```
node spikes/run-video-decode.mjs   # звук из mp4, сдвиг звука против кадров
node spikes/run-clocks-check.mjs   # часы проекта: дрейф за минуту
node spikes/run-video-sync.mjs     # свободное / со сверкой / ведомое + гейт
node spikes/run-video-drift.mjs    # первая редакция замера, оставлена как история
node spikes/run-video-diag.mjs     # диагностика оснастки (§4)
```

Замеры печатают JSON в stdout. Порты 5181–5185 — стенду на 5179 и серверу
спайков на 5180 не мешают.

Материал пересоздаётся командами ffmpeg, записанными в
`spikes/s13-video/make-media.sh`.
