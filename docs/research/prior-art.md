## 1. Презентационные движки: масштабирование сцены

Главный вопрос к ним у нас один: **как положить сцену фиксированного размера в
окно произвольного размера, не пересчитывая вёрстку.** Ответ у обоих движков
оказался одинаковый, и это хорошая новость — значит, решение устоявшееся.

### reveal.js (MIT, v6.0.1)

Проверено по исходнику `js/reveal.js`, не по документации:

```js
scale = Math.min( size.presentationWidth / size.width,
                  size.presentationHeight / size.height );
scale = Math.max( scale, config.minScale );
scale = Math.min( scale, config.maxScale );
scale = Math.round( scale * 100 ) / 100;
...
transformSlides( { layout: 'translate(-50%, -50%) scale(' + scale + ')' } );
...
dom.viewport.style.setProperty( '--slide-scale', scale );
```

Что здесь важно:

- **Логический размер фиксирован** (`width`/`height`, по умолчанию 960×700).
  Автор верстает в этих координатах и не думает про окно.
- Подгонка — **одним `transform: scale()` на контейнере**, не пересчётом
  лэйаута. Ровно то, что нам нужно: `transform` не уводит с композитора
  (наш инвариант 8).
- Масштаб **округляется до сотых** — защита от дрожания субпиксельного текста
  при ресайзе.
- Масштаб **публикуется наружу CSS-переменной** `--slide-scale`. Это ключевая
  деталь: всё, что живёт поверх сцены (у нас — оверлей редактора), должно уметь
  прочитать текущий масштаб из одного места.
- Есть `disableLayout` — режим «свою вёрстку принесу сам», и `Reveal.layout()`
  для ручного пересчёта.

**Берём идеей:** фиксированный логический размер + `scale` на контейнере +
масштаб как единственный источник правды в CSS-переменной.
**Зависимостью не берём:** reveal.js — это движок презентации целиком (свои
слайды, фрагменты, роутинг по хешу, клавиатура). Нам нужно ~40 строк из него, а
приедет всё. Плюс он тянет свою модель «слайд = шаг», а у нас сцена одна и
непрерывная.

### Slidev (MIT)

Проверено по исходнику `packages/client/internals/SlideContainer.vue`:

```js
const scale = computed(() => {
  if (slideScale.value && !isPrintMode.value) return +slideScale.value
  return Math.min(width.value / slideWidth.value, height.value / slideHeight.value)
})
const contentStyle = computed(() => ({
  height: `${slideHeight.value}px`,
  width: `${slideWidth.value}px`,
  '--slidev-slide-scale': scale.value,
}))
```

Тот же приём вплоть до деталей: фиксированный `slideWidth`/`slideHeight` в
пикселях на контенте, `Math.min` по двум осям, масштаб наружу CSS-переменной
`--slidev-slide-scale`. Отдельная ветка для режима печати — масштаб
принудительно задаётся, а не вычисляется.

**Вывод по обоим:** два независимых зрелых движка сошлись на одном решении.
Это не «один из вариантов», это стандарт. Спорить не о чем, копируем приём.

### reveal.js-plugins (MIT, Asvin Goel)

Ближайшее к нам из существующего OSS: плагин `audio-slideshow` (озвучка по
фрагментам слайда + запись), плюс `poll` и `questions` — опрос и вопросы
внутри презентации.

Это фактически «презентация с озвучкой и вопросами», то есть наш продукт в
зачаточном виде. Но модель времени там обратная нашей: аудио привязано к
фрагменту, фрагмент переключается вручную или по окончании аудио. Непрерывного
таймлайна нет, гейт как «жёсткая остановка времени» отсутствует.
**Берём:** подтверждение, что связка «слайды + озвучка + вопрос» кому-то нужна.
**Не берём:** код и модель.

## 2. Ведомый по времени рендер

### Remotion — сначала лицензия, потом всё остальное

Это самая опасная позиция в списке, поэтому разберу подробно.

**Лицензия не открытая.** В `packages/player/package.json` (версия 4.0.499)
поле лицензии — `"license": "SEE LICENSE IN LICENSE.md"`. То есть **Player
живёт под тем же нестандартным лицензионным соглашением, что и весь Remotion,
никакого исключения для него нет.** Это я специально проверял, потому что в
обсуждениях часто встречается миф «рендерер платный, а плеер бесплатный».
Миф неверен.

Условия ([terms](https://www.remotion.dev/docs/license/terms)):

- Бесплатно: физлицо; **организация до 3 человек**; НКО; период оценки.
- «A license is mandatory when the total number of personnel across all
  involved parties reaches the threshold of **four or more**» — считаются люди
  **по всем участвующим сторонам** проекта, не только штат.
- Платно: *Remotion for Automators* — $0.01 за рендер, минимум $100/мес;
  *Remotion for Creators* — $25 за место в месяц; *Enterprise* — минимум
  $500/мес.
- **Встраивание Player прямо названо** сценарием, требующим Automators.
  Показ композиции в плеере не считается рендером и не тарифицируется
  поштучно, но сам сценарий лицензируется.
- Прямой запрет: «copy or modify the Remotion Software for the purpose of
  selling, renting, licensing, relicensing, or sublicensing one's own
  derivative».
- Запрещено оказывать услугу рендеринга, где конечные пользователи загружают
  свой Remotion-код.
- С Remotion 5.0 телеметрия через `licenseKey` становится **обязательной** для
  тарифа Automators (для Creators — опциональна). Дата выхода 5.0 —
  не выяснено.

**Вывод по лицензии.** Пункт про derivative закрывает вопрос окончательно: мы
строим редактор + плеер как продукт, и любое заимствование кода Remotion —
ровно тот случай, который запрещён. Плюс порог «4 человека по всем сторонам»
мы перерастём практически сразу, а $100/мес минимума на старте — это налог на
существование. **Remotion — только идея. Ни строчки кода, ни пакета в
`package.json`.**

**Что берём идеей.** Модель «рендер — чистая функция от времени». Компонент не
владеет часами и не знает, играем мы или стоим; он вызывает `useCurrentFrame()`
и рисует то, что положено на этот момент. Время приходит снаружи. Это ровно то,
что нам нужно для инварианта «один рендер на редактор и плеер»: редактор
показывает кадр `t`, потому что пользователь встал на `t` мышкой; плеер
показывает кадр `t`, потому что там аудио. Рендер про разницу не знает.

**Что НЕ берём — и это важнее.** Я посмотрел, как у них устроены часы, и
направление оказалось противоположным нашему инварианту 1.

`packages/player/src/calculate-next-frame.ts`:

```js
const framesToAdvance =
  op((time * playbackSpeed) / (1000 / fps)) - framesAdvanced;
```

Кадр двигается от прошедшего времени в миллисекундах, квантованного по fps.
То есть **ведущий — счётчик кадров.**

`packages/player/src/set-global-time-anchor.ts`:

```js
export const ALLOWED_GLOBAL_TIME_ANCHOR_SHIFT = 0.1;
...
const newAnchor =
  audioContext.currentTime - absoluteTimeInSeconds / globalPlaybackRate;
const shift = newAnchor - audioSyncAnchor.value;
const latency = audioContext.baseLatency + safeOutputLatency;
// Skip small shifts to avoid audio glitches from frame-quantized re-anchoring
if (Math.abs(shift) < ALLOWED_GLOBAL_TIME_ANCHOR_SHIFT + latency && !force) {
  return false;
}
```

Аудио-часы (`audioContext.currentTime`) используются как якорь, но
**переякоривание происходит только когда расхождение превысило 0.1 с плюс
латентность вывода.** То есть допускается постоянный дрейф в пределах
примерно ста миллисекунд и больше.

А в `packages/core/src/use-media-playback.ts` для `<audio>`/`<video>` есть
параметр `acceptableTimeshift`: когда тег уехал дальше допустимого, его
**перематывают** к `frame / fps`.

Итого схема Remotion: кадры ведут, аудио догоняют, расхождение до ~0.1 с
считается нормой, а лечится перемоткой медиа.

**Для нас это неприемлемо дважды:**

1. Инвариант 1 говорит обратное — аудио есть время, и ничто другое время не
   двигает. Мы инвертируем схему: читаем позицию аудио, из неё считаем время
   сцены. Никакого счётчика кадров, который может разойтись, у нас просто нет,
   поэтому и переякоривать нечего.
2. Инвариант 10 требует привязки меток к словам транскрипта. Слово длится
   150–300 мс. Допуск в 100 мс на этом масштабе — это промах на пол-слова.
   Дрейф, приемлемый для генерации видео, у нас будет виден и слышен.

Ирония в том, что Remotion в итоге пришёл к `audioContext.currentTime` как к
якорю — то есть к нашему решению, но через слой компенсации. Мы берём вывод без
слоя: если аудио и есть время, компенсировать нечего.

### Motion Canvas (MIT)

Живой (последний пуш 2026-07-02, 18.8k звёзд), лицензия чистая MIT, вопросов
нет.

**Как описывается анимация.** Генераторные функции: сцена — это generator,
внутри `yield*` на анимации, `waitFor(seconds)` на паузы. Время — не параметр,
а позиция в выполнении генератора.

**Что берём идеей — `waitUntil` и time events.** Вместо «подожди 1.4 секунды»
пишется «подожди до события `intro-done`», а реальная длительность этого
события хранится **вне кода**, в мета-файле, и правится мышкой на таймлайне.
Это прямой прообраз нашего инварианта 10: в описании сцены стоит имя метки, а
не миллисекунды; сдвинули озвучку — сдвинулась метка, код не тронут.
Хорошая идея, забираем.

**Что НЕ берём.**

1. **Рендер в canvas 2D.** Дисквалифицирует как рендерер: наш плеер обязан
   быть DOM (см. последний раздел). Дальше можно не смотреть.
2. **Генераторная модель не умеет случайный seek.** В
   `packages/core/src/scenes/GeneratorScene.ts` есть `recalculate(setFrame)`,
   `reset(previousScene)` и `next()`. Чтобы попасть на произвольный кадр, сцену
   сбрасывают в начало и прокручивают вперёд шагами; тайминги приходится
   заранее считать в кеш, и «seeking through a project that contains at least
   one uncached scene will log a warning».

Второй пункт для нас критичен, но не там, где кажется. Плееру случайный seek не
нужен — инвариант 4 запрещает перемотку вовсе. А вот **редактору scrub по
таймлайну нужен обязательно**, это его основная операция. Значит наша модель
сцены должна быть **декларативной и вычислимой в точке**: `render(state, t)`
без предыстории. Генератор такого не даёт.

Это, кстати, самостоятельный аргумент в пользу инварианта 5: именно требование
«один рендер на редактор и плеер» заставляет выбрать модель, вычислимую в
произвольной точке. Если бы рендеры были разные, соблазн сделать плеер на
генераторе был бы велик — и мы бы получили редактор, который не умеет
перематывать.

### Revideo (MIT) — форк Motion Canvas, и это важный ответ на Remotion

Проверено по файлу LICENSE в `midrender/revideo` (репозиторий переехал с
`redotvideo/revideo`): **MIT**, с сохранённым `Copyright (c) 2022 motion-canvas`
— то есть это честный форк Motion Canvas, унаследовавший его лицензию.

Из README: «Revideo is a rendering engine for creating videos in code…
It ships a headless render API for generating videos programmatically and a
React player for previewing scenes in the browser… Revideo borrows concepts
from Remotion and Rive, but is, in its core, zero dep». Это движок под
коммерческим продуктом Midrender.

**Почему это стоит зафиксировать.** Revideo — это, по сути, **MIT-ответ на
лицензионную проблему Remotion**: тот же класс задачи (программное видео,
headless-рендер, React-плеер для превью), но без порога в 4 человека, без
$100/мес и без запрета на derivative. Если бы нам нужен был именно
программный рендер видео — смотреть надо было бы сюда, а не на Remotion.

**Но нам он всё равно не подходит, и по тем же двум причинам, что Motion
Canvas:** рендер в canvas 2D (`@revideo/2d`) и генераторная модель сцены
(`makeScene2D`, `waitFor`), то есть без случайного seek. Оба пункта
дисквалифицируют его как наш рендерер.

**Берём:** знание, что при необходимости экспорта видео существует живой
MIT-вариант. **Не берём:** как зависимость в v1 — экспорта у нас нет.

|---|---|
| `h5p/h5p-php-library` | **GPL-3.0**, `LICENSE.txt` — дословный текст GNU GPL v3 |
| `h5p/h5p-editor-php-library` | файла LICENSE нет; `package.json` → `"SEE LICENSE IN README.md"`; README → «All code is licensed under MIT License» |
| `h5p/h5p-interactive-video` | `library.json` → `"license": "MIT"` (v1.28.36) |
| `h5p/h5p-drag-text`, `h5p-course-presentation`, `h5p-cli` | MIT (файл LICENSE есть) |
| `h5p/h5p-multi-choice`, `h5p-blanks`, `h5p-image-hotspots`, `h5p-question-set` | **файла LICENSE нет**, но `library.json` объявляет `"license": "MIT"` |
| `tunapanda/h5p-standalone` | MIT — но это обёртка, внутри всё равно ядро |

**Ключевая находка, которая всё решает.** Клиентский рантайм H5P лежит
**внутри GPL-репозитория**: `js/h5p.js` и `js/h5p-event-dispatcher.js` отдаются
по пути `h5p/h5p-php-library/master/js/…` (проверено, HTTP 200). То есть
«h5p-php-library» — это не только PHP, там же живёт JS-ядро, в котором крутятся
все content types.

Отсюда: **content types по отдельности MIT, но запускаться они умеют только
внутри GPL-3.0 ядра.** Взять «только MIT-часть» и получить работающий виджет
нельзя. Официальная позиция самого проекта
([h5p.org/licensing](https://h5p.org/licensing)) — «H5P tries to use the MIT
license wherever possible», а GPL появился из-за стороннего кода для очистки
пользовательского ввода, и «soon the GPL code will be made optional». Обещание
это на странице висит давно; **подтверждения, что развязка состоялась, я не
нашёл — на 2026-07-27 ядро по-прежнему GPL-3.0.**

**Вывод: H5P — только идея. Зависимостью не берём ни в каком виде.** GPL нам не
подходит, а разбираться, какая именно строчка какой лицензией накрыта, в
продукте, который мы собираемся продавать, — это мина замедленного действия.

Отдельно отмечу: `h5p-editor-php-library` вообще не имеет файла лицензии и
ссылается на README. Формально это работает, но это ровно тот сорт
неаккуратности, из-за которого потом приходится объясняться с юристами
покупателя.

### Что берём идеей: каталог типов заданий

Вот ради чего стоило смотреть. Из `semantics.json` H5P Interactive Video —
**полный список того, что можно поставить на таймлайн** (проверено по файлу,
не по документации):

Blanks · DragQuestion · DragText · FreeTextQuestion · GoToQuestion ·
IVHotspot · Image · Link · MarkTheWords · MultiChoice · MultiMediaChoice ·
Nil · Questionnaire · SingleChoiceSet · Summary · Table · Text · TrueFalse

Это прямой прообраз наших гейтов, отобранный многолетней практикой в
образовании. Сопоставление с тем, что нужно нам в v1:

| Наш гейт | Аналог в H5P | Комментарий |
|---|---|---|
| выбрать вариант | MultiChoice, SingleChoiceSet, TrueFalse | база, нужна сразу |
| вписать слово | Blanks, FreeTextQuestion | Blanks — пропуски в тексте, ближе к нашему сценарию |
| перетащить элемент | DragQuestion, DragText | DragText проще: перетаскивание слов в текст |
| кликнуть по области | IVHotspot, MarkTheWords | hotspot = зона на сцене |

Совпадение с нашим списком из четырёх типов практически полное — это хороший
знак, мы не изобрели ничего экзотического и не забыли ничего очевидного.

Из неочевидного, чего у нас в списке нет и стоит подумать позже:
`MarkTheWords` (отметить слова в тексте) ложится на нашу транскрипт-модель
почти бесплатно, а `Summary` (сводка в конце) — естественный финал урока.
В v1 не тянем, просто фиксирую.

Чего сознательно не берём: `GoToQuestion` — это ветвление, а ветвления в v1
нет по решению. `Questionnaire` — сбор мнений без правильного ответа, значит и
без гейта; не наш случай.

### Живые коммерческие аналоги: рынок интерактивного видео

Смотрел на вопрос «есть ли уже живые продукты вида „видео, которое
останавливается и спрашивает“». Есть, но история категории поучительная:
**рынок за 2021–2024 годы схлопнулся.**

| Продукт | Что с ним стало | Источник |
|---|---|---|
| **Wirewax** | **поглощён Vimeo**, 6 декабря 2021. Как самостоятельный продукт не существует | [Crunchbase](https://www.crunchbase.com/organization/wirewax) |
| **HapYak** | куплен Newsela (14 октября 2021), затем **Brightcove выкупил у Newsela технологию, бренд и клиентскую базу** в конце 2021. Живёт как функция чужой видеоплатформы | [PitchBook](https://pitchbook.com/profiles/company/55582-03) |
| **Eko** | **закрыл редактор интерактивного видео 19 ноября 2024**, развернулся в сторону AI-видео для товаров | [разбор Stornaway](https://www.stornaway.io/eko-shutting-down-alternative-to-transition-interactive-videos/) |
| **PlayPosit** | жив, образовательный. От $144/год за преподавателя, институционально — по запросу | [knowledge.playposit.com](https://knowledge.playposit.com/article/323-advanced-settings-for-interactions) |
| **Mindstamp** | жив, коммерческий. $59/мес (10k минут), $79/мес, $299/мес (600k просмотров), плюс $15/мес за пользователя сверх плана | [mindstamp.com/pricing](https://mindstamp.com/pricing) |

**Гейты у выживших есть, и работают как у нас.** У PlayPosit «video playback
will pause at an interaction point… answer the question and click Submit and
continue». У Mindstamp можно «require a correct answer to continue or complete
an experience» — то есть именно жёсткая блокировка продвижения, а не мягкая
подсказка. Значит сама механика гейта рынком проверена и возражений не
вызывает; изобретаем мы не её.

**Что из этого следует для нас — три вещи.**

1. **Механика гейта — не риск.** Она работает у живых платных продуктов много
   лет. Спорить о том, «станут ли люди отвечать на вопрос посреди видео», не
   нужно.
2. **Ценность категории утекла в видеоплатформы.** Wirewax → Vimeo, HapYak →
   Brightcove. Самостоятельный «слой интерактива поверх чужого видео» оказался
   не бизнесом, а фичей: тот, у кого лежит видео, добавляет интерактив себе и
   забирает рынок. Это прямое предупреждение — **строить надстройку над
   `<video>` стратегически проигрышно**, её поглотит владелец видео.
3. **Их модель ценообразования — от просмотров и минут** ($59–299/мес за объём
   у Mindstamp), потому что они хостят и раздают видео. У нас DOM-сцена и один
   аудиофайл; трафик несопоставим. Это не только другая архитектура, но и
   другая экономика.

Из этого же вытекает, почему наша позиция принципиально иная, а не «ещё один
инструмент интерактивного видео»: мы не надстройка над видео, у нас видео
вообще нет. Подробнее — следующий раздел.

**Не выяснено:** внутреннее устройство PlayPosit и Mindstamp (какой у них
рендер оверлеев, есть ли редактор на канвасе) — публичных инженерных
материалов у них нет, а разбирать их продукт инспекцией я не стал.

### Архитектурная разница, ради которой всё затевалось

`library.json` H5P Interactive Video объявляет зависимостью `H5P.Video`.
То есть **у них внизу настоящий видеофайл, а интерактив — DOM-оверлей поверх
`<video>`.** Плеер останавливает видео и показывает поверх него виджет.

У нас **сцена и есть DOM**, никакого видеослоя под ней нет. Это не деталь
реализации, это и есть продукт:

- у H5P объекты внутри «кадра» неинтерактивны в принципе — это пиксели видео;
  кликать можно только по оверлею, который автор нарисовал сверху;
- у нас кликнуть можно по любому элементу сцены, потому что это элемент, а не
  пиксели. Гейт не «показывает виджет поверх картинки», а **разрешает трогать
  саму сцену** (снимает `pointer-events: none`);
- отсюда же доступность: у H5P содержимое видео для скринридера отсутствует, у
  нас это обычный DOM с текстом.

Это и есть ответ на «чем мы отличаемся» — формулируется в одну фразу:
*у них интерактив поверх видео, у нас видео и есть интерактив.*

И это отличие не косметическое, а защитное. Категория «оверлей поверх чужого
видео» уже показала свою судьбу: Wirewax ушёл в Vimeo, HapYak — в Brightcove,
потому что владельцу видео проще добавить интерактив себе, чем терпеть
посредника. **У продукта, где сцена и есть DOM, такого владельца сверху нет** —
поглощать нечего, надстройки ни над чем не строим.

## 4. Редакторы на канвасе

Смотрел с вопросом «взять как движок сцены редактора?». Ответ по всем —
нет, но по разным причинам: у двух проблема в лицензии, у остальных —
в архитектуре.

Сразу оговорка к названию раздела: **tldraw при проверке оказался не канвасным**
(фигуры у него DOM, канвас только под оверлеями) — подробности ниже, это
отдельно полезная находка.

### tldraw — лицензия хуже, чем принято думать

Проверено по [LICENSE.md](https://github.com/tldraw/tldraw/blob/main/LICENSE.md).
Это не «MIT с водяным знаком», как иногда пересказывают. Дословно:

Раздел **Conditions**:
> - Not to use the Software in **Production Environments**.
> - Not to disable, change, or interfere with the Software's License Key enforcement.
> - Not to remove any copyright or other notices from the Software.
> - Not to make the Software available under a license that supersedes or negates the effect of this License.
> - Not to distribute the Software or modifications of the Software as a standalone product, but only as part of another application.

Раздел **Permissions** разрешает использование только в Development
Environments.

Раздел **Technical enforcement**:
> The Software includes technical measures to verify License Key validity,
> detect deployment environments, enforce usage restrictions based on license
> type, and ensure proper watermark display. The Software may collect and
> transmit usage data to tldraw for license compliance purposes.

Плюс **Termination**: лицензия аннулируется автоматически при нарушении условий
**или если вы инициируете патентный/копирайтный иск против tldraw**.

Что это значит по факту:

- **По умолчанию продакшн запрещён вовсе.** Не «с водяным знаком», а запрещён.
  Нужен ключ: trial (100 дней, один на юрлицо), hobby (некоммерческий, с
  обязательным водяным знаком «made with tldraw» на канвасе) или коммерческий.
- **Софт технически проверяет ключ и определяет окружение**, то есть без ключа
  просто не заработает в проде.
- **Софт отправляет данные об использовании** для контроля соблюдения лицензии.
- **Цена коммерческой лицензии — не выяснено.** Страница
  [get-a-license/plans](https://tldraw.dev/get-a-license/plans) прайса не
  публикует, там форма «Speak with our sales team». В поиске фигурировала
  цифра около $6000/год за startup-тариф до 10 пользователей, но подтвердить
  её первоисточником я не смог — **считать неподтверждённой и на неё не
  опираться**.

Это source-available, а не open source, и сам tldraw это признаёт открыто:
в их [документации](https://tldraw.dev/community/license) сказано, что
лицензия «would not be Open Source by any definition».

**Не берём.** Даже если бы архитектура подходила, встроенный phone-home и
запрет продакшна без ключа — не то, на чём строят фундамент продукта.

**Но одну вещь у tldraw стоит подсмотреть, и она неожиданная.** Вопреки
названию раздела, tldraw — **не канвасный редактор**. Инспекция живого
`tldraw.com` показала ровно один элемент `<canvas>`:
`<canvas class="tl-canvas-overlays">`. **Фигуры остались DOM/SVG**, на канвас
вынесен только слой оверлеев — кисть, направляющие, ручки, курсоры соавторов
(их [issue #8314](https://github.com/tldraw/tldraw/issues/8314)).

То есть команда, которая профессионально занимается бесконечным холстом,
выбрала **DOM для содержимого и канвас только для высокочастотного оверлея**.
Их публичный аргумент за DOM-фигуры (Стив Руиз): «putting videos on the canvas
is trivial. Putting iframes on the canvas is trivial», и слой рендера
заменяем — «you can take that layer out completely and add your own».

Для нас это прямое подтверждение выбранной архитектуры, только с обратной
стороны: содержимое в DOM, отдельный слой сверху для взаимодействия. Разница
лишь в том, что нам этот слой пока незачем делать канвасным — у нас десятки
элементов, а не тысячи.

### Polotno — коммерческая, модель понятна

По [polotno.com/legal/license](https://polotno.com/legal/license):

- **$899/мес** self-serve; Enterprise — по запросу.
- Лицензия **per-application**: «Each subscription license covers one commercial
  Application under one brand family». Больше продуктов — больше лицензий.
- Исходников нет: «This Agreement does not grant access to the Polotno SDK
  source code». Доступ к исходникам — отдельный договор, порядок цены
  «low six figures».
- Триал 60 дней, **только для разработки**: «The trial may not be used for
  production, commercial use, or publicly accessible deployments».
- При прекращении оплаты «the license ends immediately and all SDK use must
  stop». Проверку лицензии обходить нельзя.

**Не берём.** $899/мес до первой выручки — это не обсуждается; плюс это
канвас, то есть архитектурно всё равно мимо.

### Konva, fabric.js, Excalidraw — лицензии чистые, архитектура нет

- **Konva 10.3.0** — MIT. Отдельно отмечу: GitHub показывает для него
  `NOASSERTION`, потому что в шапке файла два копирайта (KineticJS 2011–2013 и
  Konva 2014–present). Сам текст — дословная MIT License. Живой, пуш 2026-07-16.
- **fabric.js 7.4.0** — MIT. Пуш 2026-07-27, то есть буквально сегодня. Живее
  всех живых.
- **Excalidraw** — MIT.

Претензий к ним нет никаких, это хорошие зрелые библиотеки. Проблема одна и
неустранимая: **они рисуют в `<canvas>`.** А наш плеер обязан быть DOM.
Взять канвас в редактор — значит завести второй рендер, то есть нарушить
инвариант 5. Подробно — в последнем разделе.

Единственный сценарий, в котором Konva или fabric могли бы пригодиться, —
если бы у нас появился отдельный растровый инструмент (обрезка картинки,
рисование поверх). Такого в v1 нет.

### Библиотеки слоя взаимодействия — и неприятная находка

Это ответ на вопрос «а кто же сделает ручки ресайза, если сцена в DOM».
Лицензии проверены по файлу LICENSE, **даты публикации — по npm registry**
(это оказалось важнее лицензий):

| Пакет | Версия | Опубликован | Лицензия | Что умеет |
|---|---|---|---|---|
| `moveable` | 0.53.0 | **2023-12-03** | MIT | drag, resize, **rotate**, warp, snap, группы — над DOM |
| `react-moveable` | 0.56.0 | **2023-12-03** | MIT | то же, обёртка под React |
| `selecto` | 1.26.3 | **2023-12-03** | MIT | рамка выделения (marquee) над DOM |
| `interactjs` | 1.10.27 | 2024-03-28 | MIT | drag/resize, уровнем ниже |
| `@dnd-kit/core` | 6.3.1 | 2024-12-05 | MIT | drag-and-drop и сортировка, **не ручки трансформации** |
| `react-rnd` | 10.5.3 | **2026-03-10** | MIT | drag + resize, **вращения нет** |

**Находка, которую я обязан зафиксировать честно, потому что она меняет вывод.**
Вся связка daybrush (`moveable` + `react-moveable` + `selecto`) — а это самое
близкое к нашей задаче из готового — **не выпускала релизов с 3 декабря
2023 года**. Это два с половиной года тишины. `interact.js` — с марта 2024.

Проверено дважды: по `registry.npmjs.org` напрямую и независимой сверкой дат
последнего пуша в репозитории. Лицензия у них чистая MIT, код рабочий, но
проект застыл.

Из живого: `react-rnd` (март 2026) — но он **не умеет вращать**, а без вращения
слайдовый редактор неполон. `@dnd-kit` живой и активно развивается, но это
библиотека перетаскивания и сортировки, а не ручек трансформации — другая
задача.

**Вывод: актуально поддерживаемой библиотеки «resize + rotate + snap +
мультивыделение над DOM» на 2026 год не существует.**

Это не аргумент против DOM (на канвасе ситуация не лучше: там Konva
`Transformer` и контролы fabric — но они работают только с канвасными
объектами, которых у нас не будет). Это аргумент за то, чтобы **закладывать
слой взаимодействия как свой код, а не как чужую зависимость**.

Практический вывод: `moveable` можно взять как рабочий образец и, возможно,
как временную зависимость на первый срез — лицензия MIT это позволяет, в том
числе форк. Но планировать надо из того, что вести этот слой придётся самим.
Решение — через ADR, с явным упоминанием, что зависимость неподдерживаемая.

## Вердикт

**Зависимостью не берём ничего из «больших» проектов.** Ни Remotion (запрет на
derivative + порог в 4 человека + $100/мес минимума), ни tldraw (продакшн
запрещён без ключа, телеметрия, цена только через отдел продаж), ни Polotno ($899/мес,
per-application, без исходников), ни H5P (GPL-3.0 в ядре).

**Зависимостей-кандидатов почти нет, и это отдельный вывод.** `moveable` и
`selecto` (обе MIT, обе про DOM-редактирование) проходят по лицензии и по
архитектуре, но **не выпускали релизов с 3 декабря 2023 года** — проверено по
npm registry. Актуально поддерживаемой библиотеки «resize + rotate + snap +
мультивыделение над DOM» на 2026 год не существует вовсе. Значит **слой
взаимодействия редактора планируем как свой код**; `moveable` — образец и,
возможно, временная зависимость на первый срез, но через ADR и с явной
пометкой, что она неподдерживаемая.

**Берём идеями, поимённо:**

1. **Масштабирование сцены** — от reveal.js, Slidev **и Canva**: фиксированный
   логический размер, один `transform: scale()` на контейнере, масштаб наружу
   CSS-переменной, округление до сотых. Три независимых зрелых продукта, включая
   крупнейший в мире слайдовый редактор, сошлись на одном приёме — считаем
   стандартом и не изобретаем. Приём не просто распространён, а **нормативно
   обоснован**: CSS Transforms L1 гарантирует, что `transform` не влияет на
   поток контента, поэтому раскладка считается один раз и переносы строк не
   могут разойтись между экранами. У `zoom` такой гарантии нет — он запрещён.
2. **Рендер как чистая функция времени** — от Remotion: компонент не владеет
   часами, время приходит снаружи. Но **направление часов инвертируем**: у них
   кадры ведут и подтягивают аудио с допуском ~0.1 с, у нас аудио и есть время.
3. **Именованные метки времени вместо миллисекунд** (`waitUntil` / time events)
   — от Motion Canvas. Прямо поддерживает наш инвариант 10.
4. **Модель сцены, вычислимая в произвольной точке** — от противного, глядя на
   генераторы Motion Canvas: они не дают случайный seek, а редактору seek
   нужен. Значит `render(state, t)` без предыстории.
5. **Каталог типов гейтов** — от H5P Interactive Video. Наши четыре типа
   покрывают их ядро; на будущее отмечены MarkTheWords и Summary.
6. **Подтверждение, что жёсткая блокировка продвижения — рабочая механика**, а
   не наша выдумка: Mindstamp продаёт «require a correct answer to continue»,
   PlayPosit останавливает воспроизведение до ответа. Спорить о самой идее
   гейта не нужно.

**Главное отличие от всех аналогов, найденное в ходе обзора:** у H5P и вообще
у интерактивного видео внизу лежит `<video>`, а интерактив — оверлей поверх
пикселей. У нас сцена и есть DOM. Гейт не показывает виджет поверх картинки,
а разрешает трогать саму сцену. Это формулируется одной фразой: *у них
интерактив поверх видео, у нас видео и есть интерактив.*

**Стратегическое наблюдение, которое я не ожидал найти.** Категория
«интерактив поверх чужого видео» за 2021–2024 годы схлопнулась: Wirewax ушёл в
Vimeo, HapYak — в Brightcove, Eko закрыл редактор в ноябре 2024. Причина
структурная: тот, у кого лежит видео, добавляет интерактив себе и забирает
рынок у посредника. **Это довод не только за нашу архитектуру, но и за нашу
позицию на рынке** — у продукта, где сцена и есть DOM, владельца видео сверху
просто нет, поглощать нечего. Выжили те, кто ушёл в конкретную нишу
(PlayPosit — образование, Mindstamp — enablement), и их экономика построена на
минутах и просмотрах, потому что они хостят видео; у нас DOM и один аудиофайл,
то есть другая себестоимость.

**Отдельно на будущее:** если когда-нибудь понадобится экспорт видео, входная
точка — **Revideo** (MIT, форк Motion Canvas), а не Remotion. Тот же класс
задачи, чистая лицензия. В v1 не нужен.

**Что осталось не выяснено:**

- Дата выхода Remotion 5.0.
- Цена коммерческой лицензии tldraw — публично не публикуется, только через
  отдел продаж.
- Рендер Pitch, Gamma, Tome, Genially, Prezi, Beautiful.ai, Visme — публичных
  ссылок для инспекции найти не удалось, инженерных публикаций у них нет.
- Рендер редакторов Webflow, Builder.io, Plasmic, Framer — по косвенным
  признакам DOM в `<iframe>`, но прямой проверки нет.
- Опубликованного бенчмарка «N трансформированных абсолютных DOM-узлов → fps»
  не существует. Ориентируемся на пороги Lighthouse и на свой тест.
- Canva и Google Slides проверены на публичных маршрутах просмотра, не в
  авторизованном редакторе. Рендер сцены тот же, но оговорку фиксирую.
- Внутреннее устройство PlayPosit и Mindstamp (чем рисуются оверлеи, на чём
  сделан их редактор) — инженерных публикаций у них нет, инспекцией их продукты
  я не разбирал. Судьба категории и наличие гейтов выяснены, реализация — нет.
- Точная лицензия `h5p-editor-php-library`: файла LICENSE нет,
  `package.json` says `"SEE LICENSE IN README.md"`, README утверждает MIT.
  Формально это работает, но юридической однозначности нет.
- Обещание H5P «soon the GPL code will be made optional» — подтверждения, что
  развязка состоялась, не нашёл. На 2026-07-27 ядро GPL-3.0.

**Что было не выяснено раньше и теперь закрыто** (фиксирую, чтобы не искали
повторно): лицензия Revideo — MIT, проверена по файлу; лицензия GrapesJS —
BSD-3-Clause, проверена по тексту; судьба Wirewax, HapYak и Eko — выяснена;
рендер Canva и Google Slides — DOM/SVG, проверен инспекцией; поведение
`transform` относительно раскладки — подтверждено нормативно по CSS
Transforms L1.

## DOM или канвас

### Прямой ответ

**DOM. И это не близкий выбор.**

Причём решение принимается не по сумме плюсов и минусов, а раньше: **канвас
недостижим, не нарушив закон.**

Цепочка жёсткая:

1. Плеер обязан быть DOM. Зритель взаимодействует с элементами; нужны
   доступность, выделение текста, нативные поля ввода. На канвасе всё это
   пришлось бы писать заново и всё равно хуже.
2. Инвариант 5: один рендер на редактор и плеер, редактор импортирует рендер
   из плеера.
3. Следовательно, рендер сцены — DOM. Следовательно, сцена в редакторе — DOM.

Канвас в редакторе означал бы второй рендер. Это не оптимизация, это та самая
архитектурная ошибка, которую инвариант 5 запрещает поимённо. Так что
единственный честный вопрос — **не «что выбрать», а «во что нам это обойдётся
и терпимо ли это».** Разбираю ниже честно.

### Почему DOM-сцена вообще возможна: это гарантия спецификации, а не везение

Главное возражение против DOM-сцены звучит так: «текст перевёрстывается на
разных экранах, значит „что вижу в редакторе, то и увидит зритель“ не
выполняется, значит нужен канвас». Возражение снимается **нормативно**, и это
стоит зафиксировать явно.

CSS Transforms Level 1, [§3 The Transform Rendering Model](https://www.w3.org/TR/css-transforms-1/):

> For elements whose layout is governed by the CSS box model, **the transform
> property does not affect the flow of the content surrounding the transformed
> element.**

То есть при схеме «логическая сцена фиксированного размера (у нас 1920×1080)
плюс `transform: translate() scale()` на контейнере» **раскладка считается один
раз, в логических пикселях, и физически не может отличаться между экранами.**
Переносы строк, метрики шрифта, позиции элементов — всё посчитано до
трансформации; трансформация только рисует уже посчитанное в другом масштабе.

Это не эмпирическое наблюдение «вроде работает», а свойство, гарантированное
спецификацией. Для нашего продукта оно и есть основание доверять редактору:
автор ставит элемент, и у зрителя он будет ровно там же.

**И вот чем это отличается от `zoom`, который напрашивается как более простой
способ.** У `zoom` этого свойства нет: он влияет на раскладку, поэтому текст
при нём **перевёрстывается**, и переносы строк у автора и у зрителя разойдутся.
Внешне на глаз похоже, по сути — противоположность. Поэтому масштабируем
**только `transform`**, и это отдельный запрет в конце раздела.

Два побочных следствия из той же спецификации, которые нам на руку:

- «Any value other than `none` for the transform property also causes the
  element to establish a **containing block** for all descendants… for all of
  its absolute-position descendants» — то есть контейнер сцены автоматически
  становится системой координат для абсолютно позиционированных элементов
  сцены. Ровно то, что нужно, и бесплатно.
- «Any value other than `none` … results in the creation of a **stacking
  context**» — сцена автоматически изолирована по z-порядку от остальной
  страницы.

**Отдельно снимается главный довод против DOM для интерактивных элементов —
iOS-автозум.** Известная беда: Safari на iPhone принудительно приближает
страницу при фокусе на `<input>` с мелким шрифтом, и это ломало бы нам поля
ввода в гейтах. Но автозум смотрит на **вычисленный** `font-size`, а не на
визуальный размер после трансформации. Значит поле внутри отмасштабированной
сцены (где вычисленный размер задан в логических пикселях и достаточно велик)
**автозум не вызывает**, даже если визуально текст мелкий. Иначе говоря,
нативные поля ввода внутри DOM-сцены работают — а это ровно то, ради чего
плеер и делается на DOM.

### Что редактор реально теряет на DOM

**Производительность при большом числе элементов — теряем, но нам это не
больно.**

Канвас рисует N объектов за один проход по display list. DOM создаёт N узлов,
каждый со своим лэйаутом, покраской и композицией. Это настоящее различие, и
именно из-за него Figma, tldraw и Excalidraw ушли в канвас/WebGL.

Но у них **бесконечный холст с тысячами объектов**, а у нас **слайд**. На
слайде десятки элементов: заголовок, пара картинок, список, схема. Для
масштаба: на живой странице Canva насчитали **28 трансформированных абсолютно
позиционированных элементов** при 503 узлах всего.

**Конкретные ориентиры, а не ощущения:**

- Lighthouse ругается на размер DOM: предупреждение около **800 узлов** в
  `body`, ошибка около **1400**; отдельно флаги на глубину больше **32** и на
  родителя с более чем **60** детьми
  ([источник](https://developer.chrome.com/docs/lighthouse/performance/dom-size)).
- Показательный контрпример от monday.com: у них **даже пустые ячейки DOM не
  держали 60 fps**, и главной статьёй расхода был **Recalculate Style**, а не
  количество содержимого
  ([разбор](https://engineering.monday.com/the-power-of-the-canvas-api-a-deep-dive-into-how-we-transformed-our-table-performance-at-monday-com-part-2/)).

Из второго пункта следует правильный вывод, и он не про количество узлов:
**узкое место — не сколько узлов на странице, а сколько узлов затрагивает
пересчёт стилей и лэйаута на каждом кадре.**

Поэтому инвариант 8 (`transform` / `opacity` / `filter`) — это ровно тот
предохранитель, который делает DOM-сцену жизнеспособной: эти три свойства
проходят мимо пересчёта стилей и лэйаута, сразу к композитору. Нарушим — и
получим ту же картину, что у monday.com, на десятках элементов.

Опубликованного бенчмарка «N трансформированных абсолютных узлов → fps» не
существует — **не выяснено**, искали. Поэтому **бюджет задаём сами и проверяем
тестом** (инвариант 9 — «проверять тестом, а не верой»): предельное число узлов
на сцену плюс замер времени кадра. Если сцена уедет за бюджет, узнаем от теста,
а не от пользователя.

Отдельно: на DOM инвариант 8 (анимируем только `transform`, `opacity`,
`filter`) перестаёт быть рекомендацией и становится условием выживания. На
канвасе можно было бы анимировать что угодно; на DOM анимация `width`/`top`
на десятках узлов положит кадры гарантированно. Закон уже записан — просто
отмечаю, что на DOM за него платят немедленно.

**Точность hit-тестирования — сложнее, чем кажется в обе стороны.**

Я сначала записал это в плюсы DOM (браузер сам считает попадание, события
всплывают, `elementFromPoint` работает, повороты учитываются движком). Это
верно лишь наполовину, и поправка важная.

Стив Руиз (автор tldraw) посвятил проблеме доклад
([What's Under the Pointer?](https://gitnation.com/contents/whats-under-the-cursor)).
Его выводы, которые стоит принять как есть:

- «Hit testing is not free in the browser… it would just be spending time on
  every frame, just kind of working through that DOM, trying to find what's
  actually beneath the pointer» — то есть браузерное попадание не бесплатно,
  если дёргать его каждый кадр.
- У полых и перекрывающихся фигур порядок по Z становится неоднозначным.
- **Pointer capture ломает hit-тестирование во время перетаскивания**: указатель
  захвачен таскаемым элементом, и «что под курсором» браузер уже не скажет.

Решение, к которому пришёл tldraw и которое нам стоит взять: **держать
геометрию сцены в памяти в JS и тестировать попадание по ней**, а не по DOM —
сначала грубая фаза по ограничивающим прямоугольникам, потом точная.

**Правильная формулировка потери:** DOM даёт бесплатный `:hover`, фокус и
всплытие событий для обычного взаимодействия — и это реальный выигрыш,
особенно для плеера. Но **редактору всё равно нужна своя модель геометрии**,
потому что перетаскивание с захватом указателя и подсветка целей по DOM не
делаются. То есть эту работу мы делаем в любом случае, канвас там или DOM —
значит как аргумент в выборе она не участвует. Вычёркиваем из обеих колонок.

**Ручки ресайза и трансформы — теряем по-настоящему, и это вторая реальная
цена.**

Вот единственное место, где канвас-библиотеки дают готовое из коробки
(у Konva есть `Transformer`, у fabric — контролы). На DOM это надо строить.

Готовое под DOM формально существует — **moveable** (MIT) делает ровно это:
drag, resize, rotate, snap, направляющие, группы. Но, как показано в разделе 4,
**он не обновлялся с декабря 2023 года**, и живой замены ему нет. Так что
честная оценка: это не «одна зависимость», а **свой слой, который мы будем
вести сами**, с moveable в роли образца.

Оговорюсь, чтобы не выглядело однобоко: на канвасе `Transformer` из Konva
действительно готов и поддерживается. Это настоящее преимущество канваса — и
единственное существенное, которое я нашёл. Но оно не перевешивает: заплатить
за него пришлось бы вторым рендером и потерей интерактивности плеера, то есть
самим продуктом.

**Выделение и marquee — нейтрально.** Рамка выделения на DOM пишется как
прозрачный прямоугольник поверх плюс пересечение с закешированными рамками
элементов (готовый вариант — `selecto`, но он застыл тогда же); на канвасе
пишется руками. Паритет.

**Редактирование текста — выигрываем.** `contenteditable` неприятен, это
правда. Но на канвасе текстового редактора нет вообще: канвас-редакторы всё
равно подкладывают скрытый `<textarea>` или `contenteditable` поверх канваса и
синхронизируют с ним состояние. То есть на канвасе мы получили бы **ту же боль
плюс синхронизацию двух представлений текста.** DOM здесь строго лучше.

**Пиксельно точный растровый экспорт — теряем по-настоящему.**

Это единственная потеря, у которой нет дешёвого обхода. На канвасе есть
`toDataURL()`, и картинка готова. Из DOM растр берётся либо через
`html2canvas`, либо через SVG `foreignObject` (ограничения по шрифтам и CORS),
либо через безголовый браузер.

Насчёт `html2canvas` стоит привести его собственный README, чтобы ни у кого не
было иллюзий: снимок «may not be 100% accurate to the real representation as it
does not make an actual screenshot, but builds the screenshot based on the
information available on the page», и далее — «still in a very experimental
state, so I don't recommend using it in a production environment»
([источник](https://github.com/niklasvh/html2canvas)). У `html-to-image` та же
архитектура (DOM → SVG `foreignObject` → canvas) и те же ограничения.

То есть клиентский DOM→растр — заведомо приблизительный. Продуктовый путь для
DOM-сцены — **рендер в настоящем безголовом браузере на сервере**, а не в
странице.

**Но:** в v1 экспорта в MP4 нет по решению. То есть цена отложена, а не
уплачена. Когда экспорт понадобится, правильный путь — скриншоты/запись через
безголовый браузер (Playwright/Puppeteer), а не `toDataURL()`. Это отдельное
решение и отдельный ADR; фиксирую здесь, чтобы потом не выглядело сюрпризом.

**Z-order — нейтрально.** В DOM порядок узлов и есть порядок отрисовки
(плюс `z-index`); на канвасе — порядок в display list. Паритет.

### Как это принято решать: оверлей поверх инертной сцены

Стандартный приём для DOM-редакторов:

- **сцена рендерится обычным DOM-рендером** — тем же самым, что в плеере;
- на время редактирования **сцена делается инертной**: `pointer-events: none`;
- сверху, в тех же координатах, лежит **слой взаимодействия**: прозрачные
  hit-прокси по элементам, ручки ресайза и вращения, направляющие, рамка
  выделения. Мышь обслуживает он.

Слой знает масштаб сцены — из той самой единственной CSS-переменной (как
`--slide-scale` у reveal.js и `--slidev-slide-scale` у Slidev) — и делит на
него свою геометрию.

**Это не теория — паттерн виден в отгруженном коде.** В собранном бандле
`moveable@0.53.0` инжектируемый CSS устроен так: по умолчанию всё в оверлее
инертно, а обратно указатель включают точечно, по способностям:

```css
.guideline { pointer-events: none; z-index: 2; }
.area.avoid, .area.pass { pointer-events: none; }
.control.origin { ... pointer-events: none; }
/* и точечное включение обратно: */
:host[data-able-origindraggable] .control.origin { pointer-events: auto; }
```

Ручки (`.control`), рёбра (`.line`), направляющие (`.guideline`) и рамка
выделения (`.area`) — **абсолютно позиционированные соседи сцены, а не потомки
редактируемых элементов**. В этом и весь фокус: вся математика поворотов и
вложенных трансформов живёт в оверлее, а сцена остаётся чистой — то есть ровно
такой же, какой её отрендерит плеер.

Живая проверка подтверждает распространённость: у GrapesJS на демо-странице
**167 элементов** с вычисленным `pointer-events: none`, у Puck — **120**.

**И вот что здесь красиво.** Это ровно тот же механизм, что и наш инвариант 3.
В плеере вне гейта сцена имеет `pointer-events: none`, и трогать её физически
нельзя. В редакторе сцена имеет `pointer-events: none`, и мышь принадлежит
оверлею.

Одно и то же состояние — «сцена инертна, указателем владеет кто-то другой».
Не два механизма, а один, в двух режимах. Это сильный довод: архитектура,
выбранная под гейты, бесплатно даёт нам архитектуру редактора.

### Примеры продакшн-редакторов со сценой на DOM

Здесь нельзя верить поиску — рендер чужого продукта определяется только
инспектором в браузере. Проверяли живьём, инспекцией DOM, 2026-07-27.

**Canva — DOM. Не канвас и не WebGL.** Проверено на публичной ссылке дизайна:

- элементов `<canvas>` на странице — **0**; текст слайда — настоящий DOM-текст
  в `<span>`;
- контейнер сцены свёрстан **в проектных координатах**: `1704 × 864`, и на нём
  `transform: matrix(0.260417, 0, 0, 0.260417, 0, 0)` при
  `transform-origin: 0 0`;
- каждый элемент — `position: absolute` со своим вложенным `transform`.

То есть **Canva делает ровно то же, что reveal.js и Slidev**: вёрстка в
фиксированных проектных пикселях, подгонка одним `transform: scale()` на
контейнере. Это тот же приём, что я описал в разделе 1, найденный независимо в
крупнейшем в мире слайдовом редакторе.

WebGL у Canva есть, но только для **фильтров изображений** — это следует из их
собственного инженерного блога
([alpha-blending-and-webgl](https://www.canva.dev/blog/engineering/alpha-blending-and-webgl/)),
и посвящён он как раз тому, как смешивать WebGL-контент **с окружающими
DOM-элементами**. Инструмент рисования у них — векторные пути плюс
React-оверлей, владеющий указателем
([behind-the-draw](https://www.canva.dev/blog/engineering/behind-the-draw/)).

**Google Slides — SVG (то есть DOM). Тоже 0 элементов `<canvas>`.** Разметка
слайда — `<svg>` с `<clipPath>` и `<path>`, класс контейнера
`punch-slide-markup-surface` («Punch» — внутреннее имя Slides).

И вот деталь, которая стоит больше всего остального: **Google перевёл Docs на
канвас в 2021 году, а Slides — не перевёл.** На 2026-07-27 Slides по-прежнему
SVG. Документ с непрерывным текстом ушёл в канвас; слайд остался в DOM. Это
довольно прямой сигнал, что для слайда DOM — не компромисс, а нормальный
выбор.

**Прочее проверенное живьём:**

- **Puck** и **GrapesJS** — сцена DOM внутри `<iframe>`, `<canvas>` нет.
  В обоих видно оверлейный паттерн в чистом виде: у GrapesJS **167 элементов**
  с вычисленным `pointer-events: none`, у Puck — **120**.
- **tldraw** — гибрид: **фигуры остались DOM/SVG**, а на канвас вынесен
  **только слой оверлеев** (`<canvas class="tl-canvas-overlays">`). См. их
  [issue #8314](https://github.com/tldraw/tldraw/issues/8314) — переносили
  кисть, направляющие, ручки, курсоры соавторов, но не фигуры.
- **reveal.js, Slidev, Marp, Craft.js** — DOM.
- **H5P Course Presentation** — слайдовый редактор с DOM-сценой: элементы
  позиционируются в процентах (`height: element.height + '%'`,
  `top: element.y + '%'`), перетаскиваются через `H5P.DragNBar` (MIT).
  Прямой аналог нашего редактора, живой с 2013 года.

**Канвас/WebGL — где он действительно нужен:** Figma (свой WebGL, теперь
WebGPU), Excalidraw, Miro, Google Docs, таблицы monday.com. Обратите внимание
на закономерность: это **бесконечный холст либо непрерывный документ**, то есть
тысячи объектов и произвольный зум. Слайда в этом списке нет.

**Встречное течение 2026 года — канвасные приложения просятся обратно в DOM.**
Это стоит знать, потому что это опровергает «канвас — это будущее»:

- **Excalidraw** завёл
  [issue #11378](https://github.com/excalidraw/excalidraw/issues/11378) (май
  2026) с целью убрать свои «absolute-positioned HTML overlay hacks for active
  text inputs/areas» и вернуть «native input field focusing, text selection,
  browser translation, and accessibility tree syncing».
- **Chrome запустил origin trial HTML-in-Canvas**
  ([анонс](https://developer.chrome.com/blog/html-in-canvas-origin-trial))
  именно потому, что Google Docs, Figma и Miro упёрлись в одну стену:
  «all the powerful browser features integrated into the DOM break completely
  when the UI is trapped inside a static canvas pixel grid».

То есть те, кто ушёл в канвас, платят ровно тем, что для нас является
продуктом: интерактивностью, доступностью, нативными полями ввода и выделением
текста. Мы бы платили ту же цену, только сразу и добровольно.

**Честная формулировка теперь такая:** два крупнейших слайдовых редактора в
мире (Canva и Google Slides) держат сцену в DOM, причём Canva — тем же приёмом,
что мы собирались применить. Контрпримера — слайдового редактора, вынужденно
ушедшего в канвас из-за производительности — не нашлось.

### Рекомендация

**Сцена в редакторе — DOM, тот же рендер, что в плеере. Взаимодействие —
отдельный оверлейный слой поверх инертной сцены.**

Обоснование в порядке убывания веса:

1. Иначе нарушается инвариант 5, а альтернатива (канвасный плеер) ломает
   доступность и интерактив, то есть сам продукт.
2. **Главное возражение против DOM снято нормативно.** CSS Transforms L1
   гарантирует, что `transform` не влияет на поток контента: раскладка
   считается один раз в логических пикселях, переносы строк физически не могут
   разойтись между экранами. «Что вижу в редакторе, то и увидит зритель» — это
   свойство спецификации, а не надежда. Плюс iOS-автозум на `<input>` смотрит
   на вычисленный, а не визуальный `font-size`, поэтому нативные поля ввода
   внутри отмасштабированной сцены работают.
3. **Так делают те, кто решает нашу задачу.** Canva и Google Slides держат
   сцену в DOM/SVG (проверено инспекцией). Google перевёл на канвас Docs, но
   не Slides. Слайдового редактора, ушедшего в канвас из-за
   производительности, не нашлось.
4. Профиль нагрузки у слайда — десятки элементов, а не тысячи. Главный
   аргумент за канвас (бесконечный холст, тысячи объектов, произвольный зум)
   к нам не применяется.
5. Текст на DOM лучше, а не хуже. И это не теория: Excalidraw и Chrome
   двигают HTML-in-Canvas именно ради возврата нативных полей ввода,
   выделения и дерева доступности — того, что у нас есть по умолчанию.
6. Единственный реальный минус — растровый экспорт — в v1 отсутствует как
   задача.
7. Механизм «инертная сцена + оверлей» уже требуется для гейтов. Редактор
   получает его даром.

Что в выборе **не участвует**, хотя часто приводится: hit-тестирование. Своя
модель геометрии нужна в обоих случаях (см. выше), так что это не аргумент ни
за, ни против.

### Что это решение запрещает

Фиксирую явно, чтобы потом не спорить:

- **Нельзя вводить канвас-рендер сцены ни в редакторе, ни в плеере** — ни
  «временно», ни «для превью», ни «для производительности». Это второй рендер.
  Только через новый ADR.
- **Konva, fabric.js, Excalidraw, tldraw, Polotno — закрыты как движок сцены.**
  Konva, fabric.js и Excalidraw — по архитектуре (канвас). Polotno — и по
  архитектуре, и по лицензии. **tldraw — только по лицензии**: фигуры у него
  как раз DOM, и в другой вселенной он бы подошёл; закрывает его запрет на
  продакшн без ключа и телеметрия, а не рендер.
- **Растровый экспорт нельзя закладывать как дешёвый.** Когда дойдёт до
  экспорта — это безголовый браузер и отдельное решение, а не вызов
  `toDataURL()`.
- **Анимации строго `transform` / `opacity` / `filter`** (инвариант 8) —
  на DOM это не стилевое предпочтение, а условие, без которого посыпятся кадры.
- **Нужен бюджет на число узлов сцены и на время кадра, проверяемый тестом.**
  Ориентиры Lighthouse: предупреждение ~800 узлов, ошибка ~1400, глубина не
  больше 32. Без такого теста мы узнаем о проблеме от пользователя.
- **Нельзя тестировать попадание указателя через DOM в редакторе.** Нужна своя
  модель геометрии в памяти (грубая фаза по рамкам, потом точная) — иначе
  сломается перетаскивание с захватом указателя.
- **Нельзя рассчитывать на `moveable`/`selecto` как на живые зависимости.**
  Слой взаимодействия ведём сами.
- **Масштабировать сцену можно только `transform`. `zoom` запрещён.**
  Нормативная гарантия «раскладка одна на всех экранах» есть только у
  `transform` (CSS Transforms L1: «does not affect the flow of the content»).
  `zoom` влияет на раскладку, текст при нём перевёрстывается, и переносы строк
  у автора и зрителя разойдутся. Внешне похоже, по сути — противоположность.
- **Логический размер сцены фиксирован (1920×1080) и вшит в схему.** Любая
  «адаптивная» вёрстка внутри сцены, зависящая от размера окна, ломает то
  самое свойство, ради которого выбран DOM. Медиазапросы по ширине окна внутри
  сцены — запрещены.
- **Масштаб сцены — ровно один источник правды** (CSS-переменная), и оверлей
  обязан считать свою геометрию от неё. Два независимых вычисления масштаба —
  гарантированное расхождение ручек и элементов.
- **Модель сцены обязана быть вычислимой в произвольной точке времени**
  (`render(state, t)` без предыстории). Генераторные/последовательные модели
  вроде Motion Canvas закрыты: редактору нужен scrub.
