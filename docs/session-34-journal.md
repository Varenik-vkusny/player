# Журнал Сессии 34

Заполняется в момент находки, а не в конце. Тема сессии: «нарисовано,
но не нажимается» — класс дефектов, где орган управления автор видит,
а нажатие достаётся другому узлу. Плюс актуализация документов
(добавлено владельцем 11.08.2026).

## §2. ГЛАВНОЕ: причина тесноты холста не там, где её искал промпт

Промпт подозревал полосу свойств и панель масштаба. Замер в живом
Chromium (окно 1280×800, фикстура `two-gates`, временный спек, удалён
после снятия чисел) показал другое:

| полоса | сверху | высота |
|---|---|---|
| шапка `.ed-header` | 0 | 49 |
| полоса свойств `.ed-propbar-row` | 49 | 57 |
| **ХОЛСТ `.ed-stage-host`** | 106 | **84** |
| панель масштаба `.ed-zoom-strip` | 190 | 43 |
| панель озвучки `.ed-audio-source` | 234 | **135** |
| лента слайдов `.ed-slide-strip-wrap` | 369 | **181** |
| дорожка звука `.ed-track` | 550 | 250 |

Сумма 800. **Холст получает одну десятую окна.** Объедают его панель
озвучки и лента слайдов: вдвоём 316 px против 84 у холста.

**Механизм.** `.ed-root` — грид `auto 1fr auto` (`styles.ts:112`). Холст
сидит в строке `1fr`, нижняя колонка объявлена `auto` и берёт столько,
сколько попросит содержимое. Гибкая строка получает не долю, а **остаток**,
поэтому любой рост нижних панелей молча вычитается из холста и будет
вычитаться дальше, пока `auto` внизу не ограничен.

Дорожку (250) автор уже умеет складывать и тянуть — она не виновата.
Панель озвучки и лента слайдов не складываются никак.

начала работы. Прогоном всё равно проверяется.

## §4. Тест на класс имеет доказательство неслучайности ДО написания

Тот же замер спросил `document.elementFromPoint` в центре каждой ручки
выделенного `question`:

```
grip rotate: c=(712.9, 101.8) → div.ed-propbar      ← ДЕФЕКТ
grip nw: c=(658.4, 127.8) → div.ed-grip
grip n:  c=(712.9, 127.8) → div.ed-grip
grip ne: c=(767.3, 127.8) → div.ed-grip
grip e:  c=(767.3, 135.5) → div.ed-grip
grip se: c=(767.3, 143.3) → div.ed-grip
grip s:  c=(712.9, 143.3) → div.ed-grip
grip sw: c=(658.4, 143.3) → div.ed-grip
grip w:  c=(658.4, 135.5) → div.ed-grip
```

Восемь ручек размера достижимы, ручка поворота — нет. То есть будущий
тест обязан дать **ровно одно красное** на нынешнем коде. Ответ на вопрос
«что должно сломаться, чтобы он покраснел» получен РАНЬШЕ, чем написан
тест, а не подогнан под него потом.

Рамка выделенного текста — 15.5 px высотой, ручка стоит на `top: -26px`
от неё. Даже на холсте в 300 px объекту у верха сцены этих 26 px взять
неоткуда: запасной ход нужен независимо от правки раскладки.

## §5. Несохраняемое состояние обнуляется выбором значения по умолчанию

Складывание дорожки — локальное `useState`, между перезагрузками
не сохраняется, и это **решение владельца 06.08.2026**
(`track/TrackView.tsx:175-185`, прочитано, не по памяти): чтение
хранилища может бросить, а глушить ошибку запрещено.

Отсюда следствие для панели озвучки: сделать её свёрнутой **по умолчанию**.
Тогда несохраняемость не видна вовсе — после перезагрузки состояние ровно
то, что по умолчанию. Долг исчезает не починкой хранилища, а тем, что
хранить нечего.

## §7. Тест на класс покраснел ровно там, где предсказано

`e2e/stage-controls-reachable.spec.ts` написан ДО починок. Первый прогон:

```
Error: expect(received).toEqual(expected)
+   "ручка rotate: нажатие достаётся div.ed-propbar",
1 failed
```

Одно красное из двенадцати органов — совпало с замером §4 до единого слова.

Тест устроен так, что декоративным быть не может:
- список органов задан **явно** (`GRIPS`, `ZOOM_CONTROLS`), а не собран
  запросом по классу: собери запросом — и пропавший орган не покраснеет,
  а просто выпадет из обхода;
- перед проверкой попадания требуется, чтобы **выделение состоялось**
  (рамка видима, ручек ровно девять) — без этого обходить нечего, и тест
  зелен при полностью сломанном редакторе (грабля С33 §9);
- проверяется длина отчёта (`toHaveLength(12)`) — укороченный обход тоже
  дал бы ноль непопадаемых.

## §8. Тень меню: подстановка списка теней вместо цвета

`--ui-shadow-selected` — это готовый СПИСОК из двух теней
(`0 0 0 1px var(--ui-focus-ring), 0 10px 22px #0e131826`). Правило меню
писало `box-shadow: 0 6px 20px var(--ui-shadow-selected)` — то есть свои
числа ПЕРЕД списком. Результат — синтаксический мусор, объявление
отброшено целиком, молча.

Починка не подстановкой той же роли целиком: она начинается с кольца
фокуса и обвела бы меню цветной каймой поверх его собственной границы.
Заведена отдельная роль `--ui-shadow-overlay` для всплывающего слоя.

**Доказано сломом**, оба вывода:

```
слом (вернул 0 6px 20px var(--ui-shadow-selected)):
  ✘ у меню есть тень: объявление не отброшено разбором CSS
    Expected: not "none"          ← вычисленная тень БУКВАЛЬНО none

починка (box-shadow: var(--ui-shadow-overlay)):
  ✓ у меню есть тень …
  7 passed (8.9s)
```

Тест смотрит **вычисленный** стиль, а не текст правила: разбор CSS — это
ровно то место, где объявление пропадало. Сравнение с исходной строкой
было бы зелёным и при мусоре.

## §9. Образец цвета: из 22 px ширины 14 съедали отступы

Замер до правки: поле 22x28, `padding: 5px 7px`, `border: 1px` — на сам
образец оставалось **6.0 x 16.0**. Промпт говорил «около четырёх», порядок
тот же. Значение при этом верное: `#3b82f6` у выделенной `mover`.

Одной ширины не хватило бы: отступы заданы числом, поэтому при узком поле
забирают долю, близкую к целому. Правлены обе величины.

**Побочный эффект поймал тот же замер.** При ширине 36 полоса свойств
переставала помещаться (`scrollWidth` 598 против `clientWidth` 586), и за

невидимый образец на невидимую кнопку смысла нет; ширина уменьшена до 32,
образец **26 x 22** (площадь вчетверо с лишним), «Ещё…» на 1012 при правом
крае 1014.

Полоса была заполнена ровно под край: `scrollWidth` совпадал с `clientWidth`
до единицы. Это не запас, а совпадение, и оно не переживёт ни новой кнопки,
ни другого языка.

## §10. Холст: 84 → 214. Меньше, чем я нарисовал владельцу

Замер после правок, окно 1280x800, фикстура `two-gates`:

| полоса | было | стало |
|---|---|---|
| **ХОЛСТ** | **84** | **214** |
| панель озвучки | 135 | 33 (свёрнута) |
| лента слайдов | 181 | 153 |
| дорожка | 250 | 250 |

Развёрнутая озвучка снова забирает своё: холст падает до 112. Это
осознанное действие автора, а не поведение по умолчанию.

**Названо вслух: в наброске для владельца стояло ~300, вышло 214.** Остаток
лежит в дорожке (250, автор складывает её сам) и в карточке слайда — чтобы
лента стала 110, карточку пришлось бы ужать до ~40 px, а на такой сцену
не разглядеть вовсе. Панель масштаба (43) запаса не имеет: кнопка 24 +
отступы плашки 8 + её рамка 2 + отступы полосы 8 + линия 1 = ровно 43.

**Правило «свернуть можно только тишину».** Панель озвучки несёт
подтверждение замены, ошибку загрузки, ошибку расшифровки и отчёт
о переносе меток. Пока ей есть что сказать, она открыта принудительно,
а кнопка складывания гаснет. Проверено косвенно и сразу: три теста
`editor-audio-align` прошли БЕЗ правок — их сценарии сами разворачивают
панель этим правилом. Будь правила нет, они бы упали.

## §11. Мина масштаба: тест построен и доказан сломом

Высота холста при вписывании и есть масштаб сцены, а масштаб — это то,
через что пересчитываются все жесты мыши. Тест проверяет не «изменился ли
масштаб», а **совпадает ли он с нынешним размером холста**: первое было бы
зелёным и при пересчёте по устаревшему размеру.

Слом — подстановка запомненного `fitScale`:

```
✘ складывание озвучки пересчитывает вписывание по НОВОЙ высоте холста
  Expected: 0.1037037037037037     ← чего требует нынешний холст
  Received: 0.19814796447753907    ← масштаб от прежнего
```

Остальные **шесть** тестов масштаба при этом сломе остались ЗЕЛЁНЫМИ.
То есть новый тест держит то, чего не держал никто.

## §12. ГЛАВНАЯ НАХОДКА: слом не покраснел, и это было полезнее починки

Первая попытка сломать перенос ручки поворота (`rotateBelow → false`)
оставила оба теста зелёными. Выглядело как «тест ничего не держит» —
грабля Сессии 33 §4 в чистом виде. Причина оказалась другой.

Замер по трём фикстурам, `frame.top` в координатах полотна при пороге 26:

| элемент | `frame.top` | сторона | попадание |
|---|---|---|---|
| `two-gates/question` | 55.5 | сверху | сама ручка ✓ |
| `morph/mover` | 31.7 | сверху | сама ручка ✓ |
| `demo/bg` | 0.0 | снизу | **`div.ed-zoom-strip`** ✗ |

Два вывода, и оба важнее самой починки.

**Первый: правка раскладки САМА вылечила заявленный случай.** Холст 214
даёт `question` запас в 55 px. Тест на нём проходил мимо изменённого кода
вообще — зелёный означал «эта ветка больше не исполняется», а не «ветка
верна».

> Отсюда правило: если слом не даёт красного, сначала проверь, **исполняется
> ли ломаемый код в этом сценарии**, и только потом ищи ошибку в сломе.

**Второй: перенос ВНИЗ не лечит элемент во весь экран.** У `bg` рамка равна
полотну, и ручка под ней уезжает за нижний край области. Понадобилось
третье место — ВНУТРИ рамки, и оно безопасно по построению: сюда попадают
только рамки, у которых нет места ни сверху, ни снизу, а значит
`frame.height > canvasHeight - 52`, то есть рамка заведомо выше 26 px
и с ручками краёв не сталкивается.

Правильно построенный слом (`rotateSide` всегда `above`) даёт ровно одну
новую непопадаемую ручку у `demo/bg` и оставляет `question` зелёным.

## §13. НОВЫЙ ДЕФЕКТ, найденный тестом на класс: нижние ручки размера

Ради этого тест и затевался. У элемента **во весь экран** нижний край рамки
совпадает с нижним краем области холста, а ручки стоят ЦЕНТРОМ на краю
(`margin: -5px`). Точка ровно на границе достаётся соседу:

```
ручка s:  нажатие достаётся div.ed-zoom-strip
ручка se: нажатие достаётся div.ed-zoom-strip
ручка sw: нажатие достаётся div.ed-zoom-strip
```

**Фон нельзя потянуть за низ, и молча.** Тот же класс, что ручка поворота.

Не чинится в этой сессии сознательно: лечится отступом вокруг сцены, чтобы
её край не совпадал с краем области, а это правка вписывания — она меняет
то, что видит автор, ломает тест «полотно равно окну холста» и требует
решения владельца.

В тесте дефект **записан списком**, а не спрятан: пустой список выключил бы
проверку, `test.fail()` на весь случай потерял бы заодно ручку поворота,
которая там как раз работает. Любая НОВАЯ непопадаемая ручка сделает тест
красным; починка этих трёх — тоже, потому что список перестанет совпадать.

## §15. Полоса свойств переполнена на 464 px — но это НЕ регрессия

Посмотрел на редактор глазами (снимок из живого Chromium, чего до этого
за сессию ни разу не сделал) и увидел, что справа полоса свойств
обрывается на «По лево…», а кнопки «Ещё…» не видно вовсе.

Замер, фикстура `two-gates`, выделен текстовый `question`:

```
полоса clientWidth=586 scrollWidth=1050 переполнение=464
«Ещё…» right=1468.0 при правом крае полосы 1014.0 → попадание null
```

Из этих 464 моих — **10** (расширение поля цвета). Остальное было и раньше:
у текстового элемента полей стиля втрое больше, чем помещается в 586 px.

Отличие от ручек существенное и потому не чинится здесь: полоса
прокручивается (`overflow-x: auto`), то есть «Ещё…» ДОСТИЖИМА, просто
не видна. Ручки же были недостижимы физически.

На фикстуре `morph` полоса была заполнена ровно под край, и там я
переполнения не создал — ширина поля цвета подобрана замером именно
поэтому (§9).
