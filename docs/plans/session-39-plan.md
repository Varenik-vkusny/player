## 3. Задачи

У каждой: **слом** (что сломать, чтобы тест покраснел) и **проверка
на пустоту** (верно ли утверждение теста при ЛЮБОЙ реализации).

### 3.1. Схема v12: стили в проекте, ссылка в состоянии слайда

- `StyleSchema`: `id`, `name`, `type` (из `ELEMENT_TYPES`), `props`
  (та же карта, что `ElementState.style`);
- `id` стиля — **безопасный набор символов** `^[A-Za-z0-9_-]+$`,
  потому что он попадёт в селектор CSS. Человеческое имя живёт в `name`;
- `project.styles` — список;
- `ElementState.styleId` — необязательная ссылка;
- проверка целостности у сегмента: `styleId` указывает на существующий
  стиль, и тип стиля совпадает с типом элемента;
- миграция v11→v12: `styles: []`, ссылок нет. **Умолчание
  воспроизводит сегодняшний вид** — отсюда приёмка §4;
- новая фикстура `styles.json` (станет 21-й).

**Слом:** убрать проверку совпадения типов → фикстура со стилем текста
на фигуре обязана перестать загружаться. Убрать миграцию → тест
инвариантов №7 краснеет.

**Пустота:** «проект с пустым списком стилей грузится» верно при любой
реализации. Проверять надо, что **ссылка на несуществующий стиль
не грузится**, и что **стиль текста не встаёт на фигуру**.

### 3.2. Каскад в плеере — `applyStyles` рядом с `applyTheme`

- лист стилей создаётся кодом и вставляется **после** базовых правил
  сцены (S14: иначе молча не действует);
- селектор с приставкой контейнера: `[data-scene="…"] .st-<id>`
  (S14: две сцены на странице не смешиваются);
- элемент получает класс по `state.styleId`;
- правка стиля = переписать правило, **без пересборки сцены**;
- инвариант №5: функция живёт в плеере, редактор её импортирует.

**Слом:** вставить лист ДО базовых правил → «стиль виден на сцене»
краснеет. Убрать приставку → «две сцены не смешиваются» краснеет.

**Пустота:** «применил стиль — вид совпал» верно при любой реализации
применения (названо в промпте). Нужен тест на **ИЗМЕНЕНИЕ**: правим
стиль и смотрим, что элемент, которого не трогали, ПОЕХАЛ, а тронутый
рукой — устоял.

### 3.3. Отцепление, пометка и «вернуть как в стиле»

- признак «отличается» = ключ есть и в `state.style`, и в стиле.
  **Значения не сравниваются** (ADR-029: сравнение дало бы ложное
  «совпадает» на случайно равных);
- в панели у такого поля — пометка и кнопка;
- кнопка удаляет ключ из `state.style`, через тот же диспетчер и ту же
  отмену.

**Слом:** сделать признак сравнением значений → тест «поле, руками
выставленное в то же значение, всё равно помечено отцепленным»
краснеет. Убрать удаление ключа → «вернуть как в стиле» краснеет.

**Пустота:** «после нажатия поле показывает значение стиля» может быть
верно и без отцепления вовсе. Промежуточная проверка обязательна:
сперва убедиться, что отличие БЫЛО (иначе повторяем дефект С33,
где откат проверяли при неслучившемся первом шаге).

### 3.4. Создание стиля из элемента и применение

- «сохранить вид как стиль» — берёт ровно `STYLE_FIELDS`, не всю карту;
- применение — щелчок по стилю в панели;
- типизация: элементу предлагаются только подходящие стили.

**Слом:** разрешить применение стиля чужого типа → e2e краснеет.

**Пустота:** «после применения у элемента есть styleId» верно при любой
реализации. Проверять надо **видимое**: цвет/кегль на экране изменились.

### 3.5. Удаление стиля не тихо

- диалог с числом: «этот стиль используют N элементов»;
- при подтверждении значения стиля **впечатываются** в `state.style`
  каждого элемента — только те ключи, которых там ещё нет;
- ссылка снимается.

**Слом:** удалять без впечатывания → «после удаления вид не изменился»
краснеет (элементы сбросятся в умолчание).

**Пустота:** «после удаления стиля в проекте нет» верно всегда.
Проверять надо, что **вид элементов остался прежним**, и что число
в диалоге совпало с настоящим.

### 3.6. Сироты цвета — в существующий счётчик

- обобщить `orphan-counter`: сегодня «Проверьте N меток», станет уметь
  и цвет. **Второй счётчик не заводится** (`styles.md` §9);
- сирота цвета = ссылка на роль, которой нет в теме проекта;
- проверка идёт и по стилям, и по `state.style`.

**Слом:** подставить в стиль `var(--несуществующая)` → счётчик обязан
покраснеть. Убрать проверку стилей (оставить только элементы) →
сирота внутри стиля обязана перестать находиться.

**Пустота:** «счётчик показывает ноль на чистом проекте» пуст.
Проверять надо ЧИСЛО на проекте с известным количеством сирот.

### 3.7. Запасное значение обязательно

- запись ссылки на роль всегда даёт `var(--role, #hex)`;
- запас берётся из умолчания роли в `ThemeSchema`.

**Слом:** убрать запас → тест «элемент со ссылкой на роль, которой нет
в теме, показывает запасной цвет, а не чёрный» краснеет.
Число из S14: без запаса `rgb(0,0,0)`, базовое правило не спасает.

### 3.8. Палитры — 6–8 наборов данными

- палитра = полный набор десяти ролей (`schema.ts:111-115`: неполная
  палитра оставит роли пустыми, и сославшиеся почернеют молча);
- лежат данными, как `library.ts`, пополнение без правки React;
- выбор палитры = одна запись в `meta.theme`.

**Слом:** сделать палитру неполной → тест «каждая палитра заполняет все
десять ролей» краснеет.

**Пустота:** «палитр восемь» — тест на количество бесполезен.
Проверять надо ПОЛНОТУ каждой и что выбор перекрашивает сцену.

### 3.9. Склад наборов вне проекта

- IndexedDB, рядом с `save.ts`/`workspace.ts`, своя база;
- «сохранить набор» и «взять набор»;
- **стили КОПИРУЮТСЯ в проект** (ADR-029 §6): проект самодостаточен,
  иначе у зрителя в голом HTML сцена почернеет без единой ошибки.

**Слом:** заставить проект читать стиль со склада → e2e бандла
(инвариант №9) краснеет на голом HTML.

**Пустота:** «набор сохранился» верно при любой реализации. Проверять
надо круг: сохранил в уроке А → открыл урок Б → применил → вид совпал
с А.

### 3.10. Кисть — «Копировать формат»

Натура: у Canva это **«Копировать форматирование», Ctrl+Alt+C**,
кисти как таковой нет.

- у источника есть стиль → приёмник получает **тот же стиль**;
- стиля нет → копируются значения `STYLE_FIELDS`.

**Слом:** копировать значения вместо стиля, когда стиль есть → тест
«приёмник поехал за правкой стиля источника» краснеет. Это и есть
проверка на пустоту: совпадение вида сразу после копирования верно
в обоих случаях, различает их только последующая правка стиля.

## 4. Приёмка

**100 скриншотных эталонов совпадают в НОЛЬ пикселей без единого
перезаписанного файла.** Умолчание миграции воспроизводит сегодняшний
вид, значит красное здесь означает, что стили изменили картинку.

**Перезапись эталонов при этой правке ЗАПРЕЩЕНА.** Новая фикстура
`styles.json` добавит свои пять эталонов, и первый прогон после её
появления ОБЯЗАН быть красным: Playwright, не найдя эталона, пишет
`actual` в папку эталонов и роняет тест. Снимки смотреть глазами
до принятия.

Полный `pnpm check` в одну команду не укладывается — частями:
`typecheck`, `test:unit`, `build:player`, затем `playwright --shard=1/2`
и `--shard=2/2`. Код возврата снимать с каждой команды.

## 5. Чего не делать

- не заводить вторую машинерию каскада — писать её не понадобится;
- не класть геометрию в стиль — положить туда нечем, и так и оставить;
- не отцеплять элемент целиком из-за правки одного свойства;
- не удалять стиль молча;
- не заводить второй счётчик сирот;
- не ссылаться на роль без запасного значения;
- не заводить второй перечень полей вида в обход `STYLE_FIELDS`;
- не делать проект зависимым от склада;
- не перезаписывать эталоны не глядя;
- `styles.ts` — одна шаблонная строка, обратных кавычек ровно ДВЕ,
  hex вне блока ролей НОЛЬ;
- не менять `DUPLICATE_OFFSET` (40), `SNAP_PX` (8), `STAGE_GAP_X`/`Y`
  (24/16), ступени масштаба холста.
