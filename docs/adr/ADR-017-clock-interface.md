# ADR-017: Часы за интерфейсом, и откуда плеер их берёт

Дата: 2026-07-30
Статус: принято

## Контекст

`product.md` решением [Р] говорит: **часы — интерфейс, а не класс**, и
называет три реализации — `audio` (позиция в дорожке), `timer` (немое
объяснение по расписанию), `manual` (тренажёр, где время двигает зритель).
Код при этом знал ровно один класс: `Player` конструировал `new AudioClock`
в трёх местах, держал `AudioContext`, кэш декодированных дорожек и
собственный флаг «идёт прогрев». Расхождение записано долгом §13.1
в `planning.md`.

**Почему закрывать сейчас, а не когда появится вторая реализация.** Пока
реализация одна, извлечение механическое: ни одна строка плеера не меняет
смысла, и это проверяется прогоном тестов. Когда появится вторая, ту же
работу придётся делать под давлением сроков — и с высоким шансом, что
интерфейс подгонят под то, что уже написано, вместо того чтобы описать
им обе реализации честно.

## Решение

Два типа в `packages/player/src/clock.ts`.

```
Clock {
  duration, position, isFrozen, isRunning
  scheduleNow, scheduleEnd
  start(offset, { leadTime }), freezeAt(position), holdBeforeStart(position),
  resumeFromFreeze(), wake(), stop()
}

ClockSource {
  clockFor(src): Promise<Clock>    // часы для сегмента
  clockIfReady(src): Clock | null  // готовые прямо сейчас, без ожидания
  warm(src): void                  // прогрев на опережение
  close(): Promise<void>
}
```

`AudioClock implements Clock`, `AudioClocks implements ClockSource`.
Второй реализации пока нет и не заводится — поле режима в схему не
добавляется: это бамп версии ради поля, которое пока некому читать.

### «Шкала планирования» — нейтральное имя, а не эвфемизм

Самое интересное место интерфейса. Стык сегментов **планируется, а не
обнаруживается**: S9 намерил, что опрос в кадре даёт задержку 65 мс (это
унаследованный `outputLatency`, а не длина кадра) и щелчок раз в двадцать
переходов, а расписание — ноль и по разрывам, и по задержке.

Планирование требует от часов монотонной шкалы, в которой можно назначить
событие на будущий момент и попасть точно. У аудио это `AudioContext.currentTime`.
Называть это в интерфейсе «контекстным временем» значило бы протащить аудио
в тип, который заводится ровно затем, чтобы аудио из него убрать. Поэтому
`scheduleNow` / `scheduleEnd`, и `scheduleEnd: null` — законный ответ часов,
которые планировать вперёд не умеют (у `manual` его не будет никогда).

### Кэш дорожек переехал к источнику часов

`#tracks`, `#trackFor` и `#warming` жили в `Player`. Это подробность аудио:
у `manual` греть нечего вовсе, у `timer` — тоже. Знание «что уже готово»
теперь принадлежит `AudioClocks`, и плеер просто зовёт `warm(src)` не
задумываясь, звали ли уже.

### Умолчание в конструкторе оставлено намеренно

```ts
constructor(host, project, events = {}, clocks: ClockSource = new AudioClocks())
```

Умолчание не отменяет решения: **внутри плеера `new AudioClock` не
встречается ни разу**, и вторая реализация подставляется без единой правки
в `player.ts`. Оставлено ради инварианта №9 — встраивание в голый HTML
обязано быть одной строкой, а не ручной сборкой трёх объектов.

## Что попутно нашлось

Извлечение вскрыло дефект, не связанный с часами: `Player` держал СНИМОК
карты узлов сцены (`#nodes = new Map(this.#slides.nodes)`). С появлением
морфинга движок слайдов пересобирает сцену чаще — в момент, когда уходящие
элементы догорели, — и снимок начинал указывать на узлы, которых в документе
уже нет. Пометка кликабельных вариантов ответа (ADR-011) при этом тихо
промахивалась бы. Карта теперь читается у движка, а не копируется.

## Последствия

- `AudioClock.endsAtContextTime` переименован в `scheduleEnd`, добавлены
  `scheduleNow` и `wake()`. Транспорт редактора (`editor/src/track/transport.ts`)
  работает с `AudioClock` напрямую и не задет: ему нужна перемотка `seek()`,
  которой в `Clock` нет и не будет — у зрителя перемотки не существует.
- `Player.destroy()` закрывает источник часов, который ему дали. Это
  прежнее поведение (раньше закрывался `clock.context`), но теперь
  предположение видно в коде.
- Долг §13.1 закрыт. Долг «режим часов в схеме» НЕ открыт: он появится
  вместе со второй реализацией, а не раньше.
