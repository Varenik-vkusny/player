# ADR-004: Формат хранения проекта и версионирование схемы

Дата: 2026-07-27
Статус: принято

## Контекст

Схема — самый дорогой артефакт проекта. Код можно переписать; схему переписывать
больно, потому что от неё зависят сохранённые проекты пользователей.

Инвариант №7: любое изменение схемы = бамп версии + функция миграции + фикстура
+ тест. Без исключений.

## Варианты

**JSON + схема, описанная руками в TypeScript.** Типы и валидация живут
отдельно. Расходятся молча: тип говорит одно, проверка на загрузке — другое.

**JSON + Zod: схема как единственный источник истины, типы выводятся из неё.**
Расхождение невозможно по построению.

**Бинарный формат.** Компактнее. Отвергнут: проект должен быть читаем глазами
и различим в git — иначе эталонные фикстуры бесполезны как инструмент отладки.

## Решение

**JSON, схема описана на Zod, типы TypeScript выводятся через `z.infer`.**

```
Project {
  schemaVersion: 1
  meta:  { title, stageWidth, stageHeight }
  audio: { src, duration, words: Word[] }
  scene: Scene                              // v0: ровно одна
}

Word  { text, start, end, source: 'alignment'|'tts'|'manual', confidence? }
Scene { elements: Element[], cues: Cue[], gates: Gate[] }
Cue   { id, at: TimeRef, targetId, animation }
Gate  { id, at: TimeRef, kind, config, onWrong, maxAttempts }
```

**Механизм миграций существует сразу, с версии 1.** Реестр `1 → 2 → 3 …`,
каждая миграция — чистая функция. Загрузка неизвестной будущей версии падает
громко с понятным сообщением.

**Валидация обязательна при загрузке и падает громко.** Никаких «пропустим
битое поле» и значений по умолчанию вместо ошибки.

## Обоснование

**Почему Zod, а не рукописные типы.** Продукт живёт годами, схема будет меняться
десятки раз. Два описания одной сущности неизбежно разъедутся, и разъедутся
тихо — тип скажет, что поле есть, а проверка его не потребует. Единственный
источник истины убирает целый класс ошибок.

**Почему `source` и `confidence` в `Word` — прямое следствие S5.** Измерение
показало, что разные инструменты дают систематически разные границы слов:
`edge-tts` раньше реального звука на 43–95 мс, Deepgram позже на 30–98 мс.
Без пометки об источнике мы через месяц не отличим «тайминг гарантирован
движком синтеза» от «угадан распознавателем», а доверие к ним разное и решения
на их основе разные.

**Почему `words[]` обязателен, но может быть пустым.** Массив всегда есть —
это упрощает код. Но пустой массив делает невалидной любую ссылку вида
`{ kind: 'word' }` (см. [ADR-008](ADR-008-timeref.md)), и это ловится
валидацией при загрузке, а не падением в рантайме.

**Почему механизм миграций заводится до того, как понадобился.** Первая
миграция всегда пишется в спешке, когда уже есть пользовательские файлы.
Пустой, но работающий и покрытый тестом механизм превращает эту задачу
в рутинную.

## Последствия

**Каждое изменение схемы — это четыре изменения:** бамп версии, функция
миграции, новая фикстура, тест на миграцию старой фикстуры в новую версию.
Проверяется тестом, а не ревью.

**Эталонные фикстуры в `fixtures/projects/` неприкосновенны.** Их нельзя
править, чтобы починить упавший тест. Обновление фикстуры требует письменного
объяснения — таково правило из `CLAUDE.md`, и оно опирается на этот ADR.

**Секунды не хранятся для меток, привязанных к словам.** Они вычисляются при
загрузке из актуальных таймингов. Иначе в файле оказались бы устаревшие числа
рядом с актуальными словами.

**Чего теперь нельзя:** дублировать типы руками; добавлять поле без бампа
версии; принимать проект без валидации; хранить в проекте вычислимые величины.

**Что придётся переделать, если решение неверно:** если Zod окажется тяжёл
для бандла плеера, валидацию можно вынести из плеера в редактор и загрузчик,
оставив плееру доверенный вход. Схема при этом не меняется.
