# ADR-003: Рендер — DOM, один на редактор и плеер

Дата: 2026-07-27
Статус: принято

## Контекст

Инвариант №5: редактор импортирует рендер из плеера, двух реализаций отрисовки
быть не может. Инвариант №3: вне гейта сцена физически недоступна для кликов.
Плеер собирается без фреймворка, редактор — React.

Вопрос, который надо решить один раз: сцена рисуется в DOM или на канвасе.

## Варианты

**DOM.** Зритель взаимодействует с настоящими элементами: нативные поля ввода,
выделение текста, доступность, `pointer-events` для блокировки.
Минус, который обычно называют: перевёрстка текста при масштабировании и
меньшая производительность на сотнях элементов.

**Канвас.** Полный контроль над отрисовкой, дешёвое масштабирование, привычно
для редакторов. Минусы: интерактив и доступность придётся строить с нуля,
нативных полей ввода нет, текст надо верстать самому.

**Гибрид: канвас в редакторе, DOM в плеере.** Прямое нарушение инварианта №5.
Не рассматривался как решение, только как то, чего нельзя допустить.

## Решение

**DOM, одна функция рендера, вызываемая обоими хостами.**

Модуль экспортирует `renderScene(host, scene)`. Он не знает ни про React, ни
про аудио, ни про плеер. React-хост владеет **только контейнером** и в
`useLayoutEffect` отдаёт свой узел той же функции.

## Обоснование

**Главный довод против DOM оказался несостоятельным — нормативно, а не
эмпирически.** CSS Transforms Level 1, §3: свойство `transform` «does not affect
the flow of the content surrounding the transformed element». При схеме
«логическая сцена 1920×1080 + `transform: scale()`» раскладка считается один
раз в логических пикселях, поэтому переносы строк **физически не могут**
разойтись между экранами.

| Утверждение | Измерение |
|---|---|
| два хоста дают идентичный результат | **S7:** 0 различающихся пикселей из 921 600, матрицы трансформации совпали |
| раскладка не едет при масштабировании | **S6:** число строчных боксов совпало точно на масштабах 1, 0.5, 0.25, 0.198 |
| блокировка кликов работает физически | **S4:** `elementFromPoint` возвращает `body`, 0 из 6 кликов прошло вне гейта |

Спайк S7 построен так, чтобы доказывать не совпадение, а **невозможность
расхождения**. Сравнение двух реализаций доказало бы лишь, что сегодня они
одинаковы. Здесь второй реализации некуда взяться: она не предусмотрена
конструкцией.

Дополнительно из той же спецификации достаётся бесплатно: контейнер с
`transform` становится containing block для абсолютных потомков и создаёт
stacking context — обе вещи нам нужны.

Отдельно снят довод «нативные поля ввода на iOS сломаются»: автозум смотрит
на **вычисленный** `font-size`, а `transform` в вычисление стиля не входит.
Поле 24 px внутри сцены при масштабе 0.2 автозум не вызовет.

## Последствия

**`zoom` запрещён.** Он влияет на раскладку — текст перевёрстывается. Внешне
похож на `transform: scale`, по сути противоположен ему.

**Медиазапросы по ширине окна внутри сцены запрещены.** Сцена не адаптивна:
она как видео, везде одинакова, просто меньше. Адаптируется только обвязка
вокруг неё.

**`will-change: transform` на контейнере сцены запрещён.** Он фиксирует растр,
и при смене масштаба картинка становится мыльной. Свойство «для
производительности» здесь ухудшает результат.

**Координатные пространства нельзя смешивать.** `getBoundingClientRect` и
`clientX` учитывают трансформацию, `offsetLeft` и `clientWidth` — нет.
Масштаб берётся из DOM (`stage.getBoundingClientRect().width / 1920`),
никогда из сохранённого значения.

**Чего теперь нельзя:** рисовать сцену на канвасе в редакторе; заводить в
редакторе собственный компонент элемента сцены; полагаться на React для
отрисовки содержимого сцены.

**Что придётся переделать, если решение неверно:** если DOM не выдержит по
производительности на реальном контенте (S6 пока не закрыт), придётся вводить
виртуализацию элементов вне экрана — но не второй рендер.

## Дополнение (2026-07-28)

Решение не менялось. Уточняется фактическая поверхность модуля — то, чем
редактору разрешено пользоваться.

**Сигнатура шире, чем записано выше.** Фактически
`renderScene(host, scene, stage?)`, и она возвращает `Map<string, HTMLElement>`
— id элемента → узел. Эта карта и есть штатный и единственный способ
адресовать узлы снаружи: ни таймлайн, ни редактор не разыскивают элементы
по DOM-селекторам.

**`applyElement(node, element)` стала публичной, и это усиление инварианта №5,
а не послабление.** Редактору нужно двигать один элемент за жест. Без этой
функции наружу у него оставалось два пути, и оба хуже. Первый — вызывать
`renderScene` на каждое движение мыши: она начинается с `host.textContent = ''`
и убивает узел под курсором вместе с таймлайном, который на этот узел
ссылается. Второй — завести собственное преобразование «Element → CSS»,
то есть ровно ту вторую реализацию рендера, которую инвариант запрещает.
Функция остаётся одна на оба хоста, просто теперь её видно.

Плата за это записана в самой функции: `applyElement` приводит узел
к состоянию из схемы и стирает всё, что накрутил таймлайн поверх
(`transform`, `opacity`, `filter`). Вызывающий обязан заново выставить время.

**Появился `ScenePreview` в `packages/player/src/preview.ts`** — сцена
на заданном моменте, без звука. Класс `Player` для этого не годится и не
должен: он про часы, гейты и rAF-цикл, то есть про всё, что нужно зрителю.
Картинка на секунде T звука не требует вовсе — время приходит аргументом.

Дополнительная и вполне материальная причина: у трёх фикстур из пяти
(`minimal.json`, `two-gates.json`, `edge-cases.json`) аудиофайлов на диске
не существует. Их `audio.src` ведёт в никуда, и схема этого не ловит —
`src` проверяется только на непустоту. Через `Player` эти фикстуры не
открываются вообще.

**`segmentOf(project)` — единственная точка, через которую предпросмотр
и редактор читают `project.audio` и `project.scene`.** Это шов под будущий
граф сегментов ([`planning.md`](../planning.md) §5а): когда у каждой ноды
появится своя дорожка и своя сцена, поменяется `segmentOf`, а не всё,
что стоит выше.

Ограничение честно: шов односторонний. Сам класс `Player` пока читает проект
напрямую и через `segmentOf` не ходит. До перехода на граф это придётся
привести к одному виду.
