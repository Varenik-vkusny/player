# ADR-009: Начальное состояние анимаций и два способа выставить время

Дата: 2026-07-28
Статус: принято

## Контекст

Элемент был виден до собственной анимации появления.

Замер на `fixtures/projects/two-gates.json`, элемент `card`. У него кью
«opacity 0 → 1» на 8.000 с, а в `style` прозрачность не задана. Время
двигалось покадрово, шаг 16.7 мс:

```
кадр   0  t=0.00  opacity=""      ← карточка видна
кадр 240  t=4.01  opacity=""
кадр 300  t=5.01  opacity=""
кадр 480  t=8.02  opacity="0.002" ← только здесь появилась
```

То же с `question` (кью «y 40 → 0» на 1.0 с): до старта элемент стоял на
месте, на старте прыгал на 40 px вниз и ехал обратно. Автор пишет «появись
на слове X» — зритель видит «повиси, моргни, появись».

**Почему это не поймали раньше.** Первая попытка чинить давала правдоподобно
верные числа. При перемотке большим скачком anime.js форсирует рендер
(`forcedRender = forcedTick || deltaTime >= globals.tickThreshold`
в `node_modules/animejs/dist/modules/core/render.js`), и сломанная реализация
выглядела исправной: замер отдельными переходами на 0 / 4 / 8 / 8.2 показывал
ровно ожидаемое. Разница видна только при покадровом шаге.

Это тот же жанр ошибки, что три разбора в
[`research/spikes.md`](../research/spikes.md): способ измерения подтверждал
не свойство продукта, а сам себя.

## Решение

**Три части, каждая закрывает свою причину.**

### 1. Начальное состояние выставляется явно

`buildTimeline` перед добавлением кью кладёт нулевой кадр (`duration: 0`)
в позицию 0 для каждой пары «элемент + свойство», у которой есть кью
с явным `from`. Ключ — именно пара: у одного элемента могут быть кью
по разным свойствам, и начальное состояние у каждого своё. Побеждает самый
ранний кью — его `from` и есть то, чем свойство обязано быть до начала.

Нулевые кадры добавляются **первыми**. Порядок вставки задаёт порядок записи
в стиль, и настоящий кью обязан иметь возможность перебить установку,
а не наоборот.

Кью с `from === undefined` пропускаются: там anime.js берёт текущее значение,
и выставлять нечего.

### 2. Распорка стала таймером без цели

Распорка задаёт длительность таймлайна, чтобы время не упиралось в конец
последней анимации (обнаружено в S1). Прежний вариант вешал `opacity: [1, 1]`
на первый попавшийся узел. Если у того был собственный кью по opacity,
распорка перебивала его ровно в момент старта: у `minimal.json` на 1.250
получалась единица вместо нуля.

Теперь это `timeline.add({ duration: spanMs }, 0)` — таймер, которому нечего
перебивать, потому что он не трогает DOM вообще.

### 3. Два способа выставить время, с разными гарантиями

У `DrivenTimeline` теперь два метода. Это не удобство, а разные обещания:

| Метод | Обещание | Кто пользуется |
|---|---|---|
| `seekSeconds(t)` | дёшево; корректно при движении вперёд малыми шагами | плеер |
| `renderAt(t)` | картинка зависит только от момента, но не от предыстории; проходом через ноль | редактор, предпросмотр, скриншоты |

Плееру `renderAt` не нужен: перемотки у зрителя не существует, время идёт
только вперёд и только по кадру.

## Обоснование

`renderAt` не «на всякий случай» — обе его причины измерены.

**Первая: при движении назад значения не откатываются.**

```
прямая перемотка на 9.0        card.opacity="1"   (верно)
прямая перемотка назад на 4.0  card.opacity="1"   ← НЕВЕРНО, кью начинается только на 8.0
со сбросом в ноль, на 4.0      card.opacity="0"   ← верно
```

Без этого редактор невозможен: автор таскает головку по дорожке в обе стороны
и обязан видеть одно и то же на одной и той же секунде.

**Вторая: доигравшая анимация не перерисовывается вовсе** на повторном seek
того же времени — ветка `time >= tickableEndTime && tickablePrevTime !== duration`
становится ложной. Поэтому после точечной правки узла через `applyElement`
элемент со схемным `opacity: 0` остался бы невидимым: `applyElement` вернул
узлу состояние из схемы, а таймлайн отказался поверх него что-либо писать.

## Последствия

**Поведение плеера изменилось ровно в одну сторону:** элемент теперь скрыт
до своего появления. Ничего другого не поменялось.

**Скриншотные эталоны пересняты.** Старые фиксировали ровно тот дефект,
ради которого всё это делалось.

**Обход, который автор `demo.json` делал руками** — вписывал `"opacity": "0"`
прямо в `style`, — больше не нужен. Но и не мешает: схемное значение и `from`
самого раннего кью совпадают.

**Чего теперь нельзя:**

- Полагаться на то, что anime.js сам выставит `from` до старта кью. Он этого
  не делает: до начала твина свойство остаётся тем, чем было.
- Проверять анимации только перемоткой большими скачками. Скачок форсирует
  рендер и скрывает целый класс дефектов — проверка обязана двигать время
  покадрово.
- Вешать служебные анимации на узлы сцены. Служебное — отдельным таймером
  без цели.
