# ADR-019. Язык условий: список через И, `≠` и сравнение с числом. Схема v5

Дата: 2026-07-31
Статус: принято

## Контекст

`product.md` §2 [Р] описывает язык условий так:

> Только `переменная = значение`, `≠`, `> число`, соединённые через **И**.
> Никаких скобок, ИЛИ и свободных выражений.

Схема v4 не выполняла из этого почти ничего:

- у правила выхода ровно **одно** условие — `when: ConditionSchema`, массива нет;
- видов условий три — `equals`, `correct`, `wrong`. Нет ни `≠`, ни сравнения
  с числом.

То есть документ обещал язык, на котором нельзя было сказать ни «ответил A
**и** ответил B», ни «ответ не равен A», ни «ошибок больше трёх». Пока это
не совпадёт, обещание §2в «разные вопросы и развилки в зависимости от
переменной» невыразимо, а вместе с ним не могут появиться условные варианты
ответа (§2б [Р]) — они ждали именно языка условий.

Расхождение зафиксировано в `planning.md` и вынесено в отдельную сессию,
потому что это бамп схемы, а бамп по инварианту №7 обязан тянуть за собой
миграцию, фикстуру и тест — независимо от размера правки.

## Решение

Схема поднимается с v4 до **v5**. Меняются три вещи.

### 1. Условие получает два новых вида

```ts
ConditionSchema = discriminatedUnion('kind', [
  { kind: 'equals',    variable, value: string },
  { kind: 'notEquals', variable, value: string },
  { kind: 'correct',   variable },
  { kind: 'wrong',     variable },
  { kind: 'compare',   variable, op: 'gt' | 'gte' | 'lt' | 'lte', value: number },
])
```

`notEquals` — прямое исполнение обещанного `≠`.

`compare` несёт **оператор полем**, а не отдельным видом на каждый знак.
Документ обещал только `>`, и по букве YAGNI хватило бы вида `greater`.
Решено иначе, потому что цена ошибки несимметрична: поле с четырьмя
значениями не добавляет ни ветки в валидацию, ни элемента в интерфейс
(это один селект), а недостающее `<` стоило бы **отдельного бампа схемы**
со своей миграцией, фикстурой и тестом. Гибкость здесь дешевле долга.

### 2. Правило выхода несёт список условий, соединяемых через И

```ts
ExitRuleSchema = { id, when: array(Condition).min(1), goto }
```

Список **непустой**: правило без условий — это `default`, а он уже есть
отдельным полем, и два способа сказать одно и то же разъезжаются.

**ИЛИ не появляется** и не появится: оно получается бесплатно вторым
правилом ниже, потому что правила проверяются по порядку и выигрывает
первое подошедшее. **Скобок не будет** — с ними это перестаёт быть языком
автора и становится языком программирования.

### 3. У варианта ответа появляется необязательное условие

```ts
option = { id, label, when?: array(Condition).min(1) }
```

Вариант показывается зрителю, если условие подошло. Отсутствие `when`
означает «показывать всегда».

## Что проверяется схемой, а не надеждой

Три проверки стоят в `.refine`, потому что каждая закрывает дефект класса
«валидность не равна достижимости» — тот самый, который уже дважды стоил
этому проекту времени.

1. **Хотя бы один вариант безусловный.** Иначе при неудачном наборе
   переменных скроются все, и живой зритель упрётся в вопрос без ответов.
2. **`correctId` указывает на безусловный вариант.** Иначе верный ответ
   можно спрятать условием, и вопрос станет непроходимым — причём молча:
   схема бы это пропустила, а зритель увидел бы вопрос, на который нельзя
   ответить правильно. В задании этого требования не было, оно найдено
   при разборе формы.
3. **Непустой список условий** у правила и у варианта (см. выше).

Проверка, которую схема выразить **не может** и которая поэтому живёт
в панели проблем: сравнение с числом на переменной, ни один вариант
которой не является числом. Такое правило синтаксически безупречно
и не срабатывает никогда.

## Семантика вычисления

`conditionsHold(conditions, answers)` — это `every`. Правило подходит,
когда подошли все его условия.

**Переменной нет вовсе → условие не подошло, для всех видов включая
`notEquals`.** Это не самоочевидно: «ответ не равен красному» у зрителя,
который вообще не отвечал на этот вопрос, интуитивно читается как правда.
Решено единообразно с уже существующим поведением (`graph.ts`: переменной
может не быть, потому что гейт стоял в ветке, которую зритель не видел).
Иначе правило с `≠` тихо срабатывало бы на непройденном вопросе — то есть
вело бы зрителя по ветке, условие которой он не выполнял.

**Сравнение с числом на нечисловом значении → условие не подошло.**
Переменная хранит строку (id выбранного варианта), и `Number('красный')`
даёт `NaN`. Это законное состояние данных зрителя, а не ошибка кода,
поэтому здесь не бросается исключение. Громко падать должен код, который
сам себя сломал, а не автор, который сравнил с числом текстовый ответ, —
про него предупреждает панель проблем.

**`switch` по видам условий теряет `default`.** В v4 там стояло
`default: return false`, и это глушитель: добавь вид условия, забудь ветку —
TypeScript промолчит, а условие никогда не сработает. Дефект невидим
ни в тесте, ни в консоли, ровно как молчаливая линейная плавность anime.js.
Вместо `default` ставится исчерпывающая проверка, которая ломает сборку.

## Миграция v4 → v5

Тривиальна по построению: одно условие становится списком из одного.

```ts
when: rule.when  →  when: [rule.when]
```

Ни `notEquals`, ни `compare`, ни `option.when` в старых данных возникнуть
не могут, поэтому больше миграции делать нечего.

Двенадцать эталонных фикстур **не правятся руками и вообще не меняются**:
они намеренно лежат в разных версиях (шесть в v1, одна в v2, две в v3,
две в v4) и проверяют цепочку миграций целиком. Добавляется тринадцатая,
сразу в v5, — она и демонстрирует новый язык.

## Что решение НЕ трогает

**Переменные остаются строками.** Счётчики и арифметику («ответил верно
три раза из пяти») владелец отклонил 31.07.2026: они требуют второй
сущности — кого-то, кто умеет в переменную *писать* больше, чем id
варианта. Вопрос `planning.md` §14.10 этим закрыт.

**Идентичность варианта — `id`, не номер.** Это не менялось, а проверялось:
плеер принимает ответ, сверяя `data-id` узла со списком `options`
по `id`, и в переменную кладёт тот же `id`. Отдельной аналитики
в проекте нет. Индекс встречается только в `data-testid` и подписи
«Подпись варианта N» — то есть в оснастке, а не в данных.

## Последствия

- Инвариант №7 исполнен: версия, миграция, фикстура, тест — одним заходом.
- `product.md` §2 и схема впервые говорят одно и то же.
- Открывается дорога условным вариантам ответа (§2б) — они ждали языка.
- Появляется потребность в режиме «смотреть как зритель, ответивший X»:
  без него автор физически не может проверить условные варианты, потому что
  редактор показывает все, а зритель — часть.

## Отвергнутые варианты

**Оставить одно условие, а И выражать цепочкой сегментов.** Автор рисовал бы
служебные части без содержимого только ради логики. Структура объяснения
перестала бы отражать смысл.

**Свободное выражение строкой (`ответ == "a" && ошибок > 3`).** Требует
парсера, сообщений об ошибках парсера и обучения автора синтаксису. Прямо
запрещено §2.

**Разрешить ИЛИ и скобки.** Избыточно: ИЛИ уже выражается порядком правил.
Скобки превращают инструмент автора в язык программирования.
